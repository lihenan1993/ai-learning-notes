# Redis 事务是什么，和 MySQL 一样吗

> 本文以 Redis 7.x 为基准；实现细节以 Redis 7.2.0 官方源码核实。

## 0. 问答总结

### 0.1 Redis 事务和 MySQL 事务一样吗？

1. **不一样。** `MULTI/EXEC` 让命令连续执行，但不提供执行失败后的回滚。
2. **入队错误和执行错误要分开。** 入队阶段错误会 `EXECABORT`；执行阶段某条命令报错，其余命令仍继续。
3. **持久性另看配置。** RDB、AOF、复制和刷盘策略决定故障后能恢复多少。

### 0.2 什么时候用 WATCH？

1. **读改写冲突用 WATCH。** `EXEC` 前被改过就整笔放弃，客户端负责重试。
2. **它是乐观锁，不是回滚。** 冲突时命令尚未执行，因此不会留下半成品。
3. **集群事务的 key 必须同槽。** 可用相同 hash tag，但要警惕热点。

## 1. 详细知识点

## 1. 默认路径：命令打包，不是数据库事务

**一批命令在入队前已经写死，只要求 `EXEC` 时连续跑完、别的客户端插不进来，用 `MULTI` / `EXEC`。广告库存扣减若逻辑是「固定两步写入、不依赖中间读结果」，可以这样打包；一旦需要「先看库存再决定扣不扣」，不要硬用事务，改 Lua 或 `WATCH` 重试。**

业务 key 例如 `stock:sku:10086`、`sold:sku:10086`。

```
MULTI
  DECR stock:sku:10086
  INCR sold:sku:10086
EXEC
```

| 命令 | 作用 |
|---|---|
| `MULTI` | 开启事务。之后命令只入队，回 `QUEUED`，先不执行 |
| `EXEC` | 按入队顺序一口气执行，返回每条结果的数组 |
| `DISCARD` | 丢掉队列，事务结束 |
| `WATCH key ...` | 监视 key；`EXEC` 前被别人改过则整笔失败（返回 `nil`） |
| `UNWATCH` | 取消监视；`EXEC` / `DISCARD` / 断连也会自动清 |

### 防插队长什么样

普通情况下两个客户端的命令会交错：

```
客户端 A: GET stock:sku:10086
        ↓
客户端 B: SET stock:sku:10086 0
        ↓
客户端 A: DECR stock:sku:10086   # 读到的值已经过时
```

事务把入队和执行拆开：

```
MULTI 之后     命令进本连接队列，不执行
        ↓
EXEC 时        队列连续跑完，再处理别的连接
        ↓
期间别的客户端的 SET / INCR 插不进来
```

Redis 里说的「原子」，在这里指**连续执行、中间不插队**，不是全部成功或全部撤销。单线程模型保证了这一点，见 `20-redis单线程模型.md`。

### 两种失败必须分开说

| | 入队就错（语法、参数个数） | 执行时才错（类型不对，如对字符串 `INCR`） |
|---|---|---|
| 何时发现 | `MULTI` 和 `EXEC` 之间 | `EXEC` 正在跑 |
| 结果 | Redis 2.6.5+：`EXEC` 拒绝，**一条都不跑** | 这条报错，**其余照执行** |
| 回滚？ | 没有可回滚的（还没执行） | **不回滚** |

所以 Redis 事务的核心保证是：执行时不插队，以及入队错误或 `WATCH` 冲突时整笔不跑。它没有执行出错后的撤销机制，也不提供 MySQL 那样可配置的事务隔离级别。

为什么不回滚：单线程里做 undo 又慢又复杂。设计取舍是——命令写对了就连续执行；类型不匹配视为调用方写错，不替你撤销。半成品要业务自己兜：幂等、补偿、或别把「必须全有或全无」的逻辑交给 Redis 事务。

## 2. WATCH：乐观锁，变了就放弃

**读改写冲突用 `WATCH`：先盯住 key，`EXEC` 前发现版本变了就整笔不跑，客户端重试。冲突不频繁时够用；冲突很高、或逻辑要按中间结果分支，直接上 Lua，少在客户端空转重试。**

扣库存的典型形状：

```
WATCH stock:sku:10086
GET stock:sku:10086          # 读到 5
        ↓ 业务判断够不够
MULTI
  DECR stock:sku:10086
  INCR sold:sku:10086
EXEC
  ├── 返回结果数组 → 已执行，仍需逐项检查是否有命令报错
  └── 返回 nil     → 被人改过，整笔取消，自己重试
```

`WATCH` 是乐观锁 CAS：提交时发现变了就放弃。失败时命令还没开始跑，所以**不会**出现「已经执行了一半再撤回去」——因为根本没跑。

### `UNWATCH` 和连接池

监视挂在**当前连接**上。读完发现不用改（比如库存已是 0），若不解开就还连接，下一个请求会带着别人的监视，`EXEC` 可能无故失败。`EXEC` / `DISCARD` / 断连会自动清；只有「WATCH 了却不走这三条」才需要手写 `UNWATCH`。

### 集群边界

`WATCH`、事务涉及的 key 必须落在同一 hash slot。跨 slot 的 `stock:sku:10086` 和 `order:pay:{order_id}` 不能塞进同一笔事务。要用 hash tag 把相关 key 钉到同槽，例如 `stock:{sku:10086}` 与 `sold:{sku:10086}`，见 `140-redis高可用.md`。

## 3. 和 Lua、Pipeline 的边界

**事务做不到「入队时根据 `GET` 结果决定下一步」——入队时命令还没执行，看不到中间结果。要读了再决定怎么写，用 `WATCH` 重试，或直接写 Lua。Pipeline 只省 RTT，不保证中间不插队，和事务不是一回事。**

| | `MULTI` / `EXEC` | Lua | Pipeline |
|---|---|---|---|
| 防插队 | 是 | 是 | 否 |
| 出错回滚 | 否 | 否 | 无关 |
| 中间结果决定下一步 | 否 | 能 | 无关 |
| 集群 | key 同槽 | key 同槽 | 无此约束（按条路由） |

怎么选见 `75-pipeline事务和lua.md`。分布式锁那种「先确认还是自己的 token 再删」属于读后写，见 `130-redis分布式锁.md`。

## 4. Redis 事务满足 ACID 吗？

**不完全满足。`EXEC` 保证队列执行期间不被其他客户端命令插入，但执行错误不回滚；业务一致性需要应用保证，持久性取决于持久化配置。不能简单记成「一致性、隔离性完全保证，原子性、持久性不支持」。**

### 先用银行转账理解 ACID

以「账户 A 向账户 B 转 100 元，无手续费」为例：

| 特性 | 核心含义 | 转账中的要求 |
|---|---|---|
| **原子性（Atomicity）** | 要么全部生效，要么全部不生效 | A 扣款和 B 入账必须一起成功；失败不能只留下扣款 |
| **一致性（Consistency）** | 事务前后满足已定义的约束和业务规则 | A、B 总金额不变；若业务禁止透支，A 余额不能为负 |
| **隔离性（Isolation）** | 按隔离级别约束并发事务之间的影响 | 其他事务不能随意观察或干扰转账中间状态；具体读到什么取决于隔离级别和读取方式 |
| **持久性（Durability）** | 提交成功的修改能够在故障后恢复 | 收到提交成功后，宕机重启仍能恢复转账结果 |

几个容易混淆的点：

- **一致性不会自动识别所有业务规则**：数据库负责已声明的约束，应用仍要正确实现转账、余额检查等逻辑。原子性与隔离性帮助维护一致性，但不能修正错误的业务代码。
- **隔离性不是所有级别都「完全互不干扰」**：例如读未提交可能脏读；在读已提交下，用两条查询分别读取 A、B，也可能跨越一次转账，拼出不一致的总额。
- **持久性不要求数据页立刻全部写盘**：关系数据库通常先持久化提交所需的日志，再通过日志恢复数据。保证范围仍取决于刷盘配置和存储可靠性。
- **ACID 的一致性与 CAP 的一致性不同**：前者关注约束和业务语义；CAP 中的 C 通常指线性一致性，即读写表现得像访问一个遵守实时顺序的单一副本，并非简单要求「副本实时同步」。

### 对照 Redis 的实际保证

| 特性 | Redis `MULTI` / `EXEC` 的保证 | 边界 |
|---|---|---|
| **原子性（A）** | 保证执行不被插队；入队错误、`WATCH` 冲突时整笔不执行 | 执行期某条命令失败，其余命令继续，已生效修改不回滚；不具备完整的 ACID 原子性 |
| **一致性（C）** | 每条命令遵守自身的数据类型与操作规则 | 不自动维护跨 key 的业务约束；部分命令失败可能直接破坏总额守恒等规则 |
| **隔离性（I）** | 同一节点上，`EXEC` 内的命令连续执行，其他客户端命令不能插入 | 保证范围是执行阶段；`WATCH` / `GET` / `MULTI` 之间仍可有其他操作，需要冲突检测与重试 |
| **持久性（D）** | 依赖 RDB、AOF 及其刷盘策略 | 事务本身不额外保证落盘；本地落盘也不等于故障切换后一定不丢数据 |

**不要把 Redis 的执行串行直接等同于「整段业务逻辑处于最高隔离级别」。** 如果先在事务外读余额再入队扣款，读到的余额可能已过时；需要 `WATCH` 在冲突时取消并重试，或用 Lua 将检查和修改放到一次执行中。Lua 同样不提供出错回滚，应尽量在写入前完成条件与类型检查。

### 转账反例：不插队，也可能只扣不加

```text
SET account:A 1000
SET account:B invalid

MULTI
DECRBY account:A 100
INCRBY account:B 100
EXEC
# 第一条成功：A = 900
# 第二条失败：B 不是整数，无法加款
# A 不会恢复到 1000
```

这笔事务执行时没有其他客户端插队，但仍然留下「A 已扣款、B 未入账」的结果：**缺少失败回滚，既破坏原子性，也可能破坏业务一致性。** `EXEC` 返回结果数组不代表每条命令都成功，客户端必须检查每一项结果。

### 持久性要看配置，不能一概说不保证

| 配置 | 收到成功响应后的持久性边界 |
|---|---|
| 不开启持久化 | 仅在内存中，进程退出或机器故障后无法靠本地持久化恢复 |
| 仅 RDB | 只能恢复到最近一次成功快照；之后的修改可能丢失 |
| AOF `appendfsync no` | 由操作系统决定何时刷盘，故障时可能丢失尚未落盘的数据 |
| AOF `appendfsync everysec` | 通常每秒刷盘，故障时通常可能丢失约 1 秒的数据，异常情况下可能更久 |
| AOF `appendfsync always` | 在正常存储和刷盘语义、未跳过同步的前提下，写入刷盘后才确认成功，提供最强的本地持久性，代价是更多磁盘同步开销 |

`always` 不能简单理解成「仍必然有一个成功响应后丢数据的小窗口」：关键是确认成功前是否完成持久化，以及存储是否可靠。异步复制下，主节点即使已经本地落盘，故障切换到尚未收到该写入的副本仍可能丢失数据，这是另一层保证。

**记忆：A 管全部生效或全部撤销，C 管业务规则，I 管并发影响，D 管提交后恢复。Redis 事务重点保证执行不插队，不提供失败回滚，C 靠业务设计，D 看持久化与复制配置。**

## 补充：Redis 事务、`WATCH` 和 MySQL 事务

| | 机制 | 解决什么 | 不解决什么 | 核心代价 |
|---|---|---|---|---|
| **`MULTI` / `EXEC`** | 入队后连续执行 | 一串已知命令中间不插队 | 出错回滚；入队时看不到中间结果 | 执行期单条失败会留下半成品状态 |
| **`WATCH`** | 乐观锁 CAS：监视 key 变了则 `EXEC` 失败 | 读改写冲突时整笔不跑 | 不替你重试；不提供悲观锁 | 冲突高时客户端反复重试 |
| **MySQL 事务** | undo + 隔离级别 | ACID、出错可 `ROLLBACK` | — | 日志与锁开销，和 Redis 不是一层 |

## 对照记

```
Pipeline（见 75）
  ↓ 解决了少 RTT；中间可以插队，不是事务
MULTI / EXEC
  ↓ 解决了连续执行不插队；执行期失败不回滚，看不见中间结果
+ WATCH
  ↓ 解决了乐观并发；冲突高时靠客户端重试，跨 slot 做不了
Lua
  ↓ 解决了先读后写的原子判断；也不回滚，长脚本堵主线程
MySQL 事务
  ↓ 支持整笔 ROLLBACK；部分错误只撤销当前语句，应用仍需正确处理
```
一句话：**Redis 事务是打包连续执行，不是 ACID 回滚；入队语法错整笔放弃，执行类型错继续跑；`WATCH` 变了就重试，跨 slot 别硬上，先读后写用 Lua。**
