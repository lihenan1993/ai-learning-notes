# Redis 分布式锁怎么做

> 本文以 Redis 7.x 为基准；实现细节以 Redis 7.2.0 官方源码核实。

## 0. 问答总结

### 0.1 Redis 分布式锁的最小正确实现是什么？

1. **加锁用一条 `SET key token NX PX ttl`。** NX 保证互斥，TTL 防死锁，token 标识所有者。
2. **解锁和续期必须比较 token 后再操作。** 用 Lua 把比较与删除或续期放在一次执行中。
3. **锁只提供有限时间内的互斥。** 业务正确性仍要靠数据库约束、幂等和版本校验。

### 0.2 主从切换会不会丢锁？

1. **会。** 加锁成功尚未复制就发生故障转移，新主可能没有锁。
2. **token 只能防误删。** 它不能撤销已经发生的双持有。
3. **零容忍场景使用共识系统。** Redlock 有多数派和时钟假设，不能当成绝对安全证明。

## 1. 详细知识点

## 1. 加锁三要素：NX、EX、token

**一行命令同时满足互斥、防死锁、可识别持有者：`SET lock:order:1001 <token> NX EX 30`。不要拆成 `SETNX` 再 `EXPIRE`，中间崩溃会留下永不过期的锁。value 必须是本客户端唯一 token，不能只用固定字符串 `1`。**

```
客户端 A
        ↓
SET lock:order:1001 a7f3-... NX EX 30
  ├── 成功 → 进入临界区（改订单、跑定时任务）
  └── 失败 → 放弃 / 等待再抢
```

库存串行、同一用户下单串行、定时任务防重，都是这个形状。锁只管互斥，不管业务对不对。

### 为什么 value 要放 token

只有 key、没有身份，解锁只能 `DEL lock:order:1001`。典型事故：

1. A 拿到锁，卡死 / 网络分区，TTL 到期  
2. B 拿到同一把锁，开始干活  
3. A 恢复，执行 `DEL` → 把 B 的锁删了  
4. C 再进来，B 与 C 同时持有  

所以解锁、续期都必须带上 token，对得上才动。

---

## 2. 续期（看门狗）：短 TTL + 活着就续

**`EX 30` 两头不讨好：业务超过 30 秒则锁先过期，别人进来双持有；TTL 设成 1 小时则持有者崩溃后别人干等。默认短 TTL，另起后台心跳（看门狗）周期性续租，例如每 10 秒把 TTL 拉回约 30 秒。进程挂了没人续，最多几十秒自动释放。**

```
加锁成功，TTL=30s
        ↓
后台每 10s：
  Lua：仍是我的 token？ → PEXPIRE 拉回 30s
                 不是我的 → 停止续期（已丢锁）
        ↓
业务结束 → 主动解锁并停看门狗
```

续期本身也是 Lua：先确认还是自己的锁，再 `PEXPIRE`。不能无脑给任意 key 续，否则会给别人的锁续命。

### 代价

续期线程还在、业务线程已死锁或卡死时，锁会被续很久，别人进不来。看门狗解决的是「活着的持有者不够 TTL」，不是「假活」。临界区要有超时与可取消，不能无限续。

---

## 3. 解锁：Lua 校验 token 再删

**比较与删除必须在同一段 Lua 里。拆成 `GET` 再 `DEL`，中间别人能插队。确认是自己的 token 后 `DEL`，需要叫醒等待者时再 `PUBLISH`。**

```lua
if redis.call('GET', KEYS[1]) == ARGV[1] then
  return redis.call('DEL', KEYS[1])
else
  return 0
end
```

| 时机 | 不检查会怎样 |
|---|---|
| 解锁 | 误删别人的锁（A 删 B） |
| 续期 | 锁已是别人的，还给它续 TTL |
| 可重入 | 分不清自己重入还是别人占着；value 旁记计数，减到 0 才真正删 |

---

## 4. 没抢到锁：自旋还是订阅

**互斥意味着同一时刻只有一个人成功。其他人要么放弃，要么等待。等待默认自旋轮询（短睡眠再 `SET NX`）；抢的人多、空转打 Redis 太贵时，再升级为订阅解锁频道，持有者解锁时 `PUBLISH`，等待方被叫醒后再抢一次。订阅只叫醒，不保证下一个一定是你。**

| | 自旋轮询 | 订阅解锁频道 |
|---|---|---|
| 怎么做 | 循环再 `SET NX`，中间可短 `SLEEP` | 订 `channel:lock:order:1001`；解锁时 `PUBLISH` |
| 优点 | 实现简单 | 少空转，锁一放就能醒 |
| 缺点 | 竞争激烈时浪费 Redis QPS | 实现绕；惊群后仍要再抢 |

也可以设等待上限，超时当失败。业务允许「抢不到就算了」的，不必等。

---

## 5. 主从切换丢锁与 Redlock 争议

**单主（或集群里一个 slot 的一个主）上的锁，扛不住「加锁成功尚未复制、主就挂了」。从升主后锁键消失，另一个客户端再加锁成功，出现双持有。解锁时校验 token 防的是误删，补不回已经发生的并行临界区。**

```
A 在旧主 SET 成功（尚未复制到从）
        ↓
旧主挂，从升主（没有 lock:order:1001）
        ↓
B SET 成功  ← 此处已双持有
        ↓
A 仍在跑业务；A 稍后解锁：新主上对不上 token，不 DEL
  → 只避免误删，互斥早已破坏
```

### Redlock 做什么

对 N 个独立 Redis（常见 5 个，不要拿一套主从凑数）分别加锁，多数派（N/2+1）成功且总耗时仍在有效期内才算拿到；释放时每个都解。挂一台，多数派还在，不会随单主切换丢锁。集群上「按 hash 选一个节点」仍是单 key 锁，不是 Redlock。

### 争议与代价（Kleppmann vs Sanfilippo）

Martin Kleppmann 指出：Redlock 的安全依赖客户端对「锁有效剩余时间」的计时。NTP 时钟跳变、长时间 GC / 停顿后，进程以为还持有，TTL 实际已过，别人已进入临界区。Salvatore Sanfilippo（antirez）认为在假设时钟大致单调、停顿受控时 Redlock 实用。面试要能说出两边的点，而不是背「Redlock 一定对 / 一定错」。

| 代价 | 说明 |
|---|---|
| 延迟与运维 | 一次加锁打 N 个实例；多套独立 Redis，不能复用一套主从 |
| 时钟与停顿 | 有效期靠客户端计时；对时跳变、GC 停顿可破互斥假设 |
| 仍非共识锁 | 比单主强，但不是 ZK / etcd 用共识维护的锁 |

多数业务：单主 `SET NX EX` + token + Lua 解锁 + 续期够用，接受「主突然挂、极短窗口可能双持有」，关键正确性放 MySQL（唯一索引、事务、行锁）。对双持有零容忍，别只靠单 Redis；上 Redlock 也要认清时钟代价，或直接用 ZK / etcd。

```
Redis 锁     互斥、降并发，高可用优先，允许极短双持有
MySQL        最终说了算，强一致
```

## 补充：锁的各个要素解决什么

| 要素 | 解决什么 | 不解决什么 |
|---|---|---|
| **NX** | 互斥：只有一个人 `SET` 成功 | 持有者崩溃后的释放 |
| **EX / PX** | 自动过期，避免死锁 | 业务跑超 TTL 时的误释放 |
| **token（UUID）** | 解锁 / 续期只动自己的锁 | 主挂复制未跟上造成的双持有 |
| **看门狗续期** | 短 TTL 与长任务兼顾 | 进程假活（卡死但续期线程还在） |
| **Redlock** | 抗单实例切换丢锁 | 时钟漂移、GC 停顿下的绝对互斥 |

## 对照记

```
单机锁
  ↓ 一个进程里互斥
SET NX EX
  ↓ 跨进程互斥，无身份、固定 TTL
+ token + Lua 解锁 / 续期
  ↓ 只改自己的锁（不解主挂丢锁）
+ 看门狗续期
  ↓ 活着就续，挂了自动过期
没抢到：放弃 / 自旋 / 订阅再抢
  ↓ 等与醒，不保证下一家是你
集群单 key
  ↓ 仍怕单主切换丢锁
Redlock（多数派）
  ↓ 抗单实例挂，贵、靠时钟假设
ZK / etcd
  ↓ 共识，更重，互斥更硬
```

一句话：**分布式锁用 `SET NX EX` + token + Lua 解锁与续期完成跨机器互斥；看门狗兼顾短 TTL 与长任务；Redlock 抗单主丢锁但吃时钟与运维，强一致仍放 MySQL。**
