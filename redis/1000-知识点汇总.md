## 基础

- 问：Redis 为什么快？
  答：Redis 把主要读写放在内存，使用紧凑编码减少小对象的指针和分配开销，再以 I/O 多路复用同时服务大量连接；命令由主线程串行执行，避免锁竞争和上下文切换。它不是计算能力无限强，单实例通常先受网络带宽、RTT、内存容量和慢命令限制。

- 问：Redis 是单线程吗？
  答：命令执行主线程是单线程，一条命令跑完才轮到下一条，因此慢 Lua、扫描大集合或大 key 删除会堵住整个实例。网络 I/O、持久化和异步释放可由其他线程或子进程辅助，但这不等于多条命令并行执行。

- 问：Redis 有哪些基本数据类型？
  答：基本类型是 String、List、Hash、Set、ZSet；先按业务操作选型，而不是按“哪个底层更快”选型。Redis 会按规模在 listpack、intset、hashtable、skiplist 等编码间转换：小对象优先省内存，大对象再换取按成员定位、排序或两端操作的效率。

- 问：Bitmap、HyperLogLog、GEO 怎么选？
  答：Bitmap 用 String 的 bit 做精确 0/1 状态及按位交并，适合签到和日活；HyperLogLog 以约 12KB 估算海量去重计数，标准误差约 0.81%，不能列出成员；GEO 基于 ZSet 做附近搜索。需要精确成员名单或集合运算时用 Set，不要把 HLL 当精确去重。

- 问：排行榜和延时队列怎么用 ZSet 做？
  答：排行榜将 score 作为业务分值，用 `ZREVRANGE` 查 Top N、`ZREVRANK` 查名次；延时队列将 score 作为到期时间戳，轮询取 score 不大于当前时间的任务。两者都是单 key 排序，成员过多会成为大 key，延时队列也没有 Stream 那样的消费组和 ACK。

- 问：过期和淘汰是一回事吗？
  答：不是。过期处理带 TTL 的 key 到期后怎么删除，默认由惰性删除加定期抽样删除配合；淘汰处理内存达到 `maxmemory` 后继续写入时该踢掉谁，由 `maxmemory-policy` 决定。设了 TTL 不代表内存会在到点瞬间释放，TTL 也不等于淘汰策略。

- 问：为什么不能存大 key？
  答：大 key 指单个值体积大或集合成员多；它未必放不下，但一次读写会占满网络，大集合的遍历或 `DEL` 会堵主线程，复制、RDB/AOF 和集群迁移也要搬整份数据。拆成多个可控的小 key，删除大集合用 `UNLINK` 或渐进式删除；不要只看总内存而忽略单 key 大小。

- 问：什么是热 key？
  答：热 key 是 QPS 极高的单个 key，所有请求会集中到同一个 slot 和分片，可能打满该节点 CPU、网卡或连接，使同节点其他 key 也超时。扩容和加从库不能把一个 key 拆开；默认用热点探测加本地缓存挡读，读极热且写少时才复制多份 key 打散 slot。

## 原子操作与持久化

- 问：Redis 事务和 MySQL 事务一样吗？
  答：不一样。`MULTI` / `EXEC` 将一组命令入队后连续执行，期间其他客户端不能插队；入队阶段语法错误会让整笔不执行，执行阶段类型错误则该命令报错、其余命令继续，Redis 不提供回滚。需要“读值后判断再写”时用 Lua，或用 `WATCH` 做乐观锁重试。

- 问：Pipeline、事务、Lua 怎么选？
  答：Pipeline 只是把多条独立命令批量发出，减少 RTT，不保证原子性；`MULTI` / `EXEC` 适合一组预先确定的命令连续执行；需要读取中间状态、条件判断和写回时用 Lua 在服务端原子完成。三者都不是 MySQL 事务，执行失败没有自动回滚。

- 问：Redis 持久化怎么选？
  答：缓存可由 MySQL 或上游重建、能接受快照间隔内的数据丢失时，RDB 通常够用；作为准数据源、希望尽量少丢时开 AOF，并按 `appendfsync` 策略选择性能和丢失窗口。RDB 体积小、恢复快，但 `BGSAVE` 的 `fork` 和 COW 需要预留内存；AOF 更重，还需要关注刷盘抖动和重写。

- 问：RDB、AOF、混合持久化分别是什么？
  答：RDB 是某个时点的内存全量快照；AOF 追加改变数据集的写命令，靠刷盘策略控制最多丢多少。Redis 7.2 的重写 AOF 是 Multi-Part AOF：base 文件加 incr 文件，由 manifest 组织；混合持久化用 RDB 镜像作 AOF 前缀、后接增量命令，兼顾加载速度和完整性。

- 问：Redis 能当消息队列吗？
  答：能做短积压、可补偿的轻量队列：List 是竞争队列，`POP` 后即删且没有 ACK；Pub/Sub 只给在线订阅者，不落盘、不补发；Stream 有消费组、PEL、`XACK` 和 `XCLAIM`，能做到至少一次。需要长积压、分区扩展、死信和成熟运维能力时用 Kafka 或 RocketMQ，不要让 Redis 承担企业级消息总线。

## 缓存与流量

- 问：常用缓存更新策略怎么选？
  答：Redis 配 MySQL、读多写少时默认 Cache Aside：读 miss 查库再回填，写时先改 MySQL 再删 Redis，通常只删不改以避免复杂视图被写错。Read/Write Through 让缓存组件代管加载或同步写库；Write Behind 先写缓存、异步刷库，吞吐高但宕机可能丢未刷数据，只适合能容忍这种窗口的场景。

- 问：分布式限流默认用什么？
  答：默认用令牌桶：按固定速率补 token，并允许桶内积攒的有限突发；判断、补充和扣减必须在一段 Lua 中原子执行。固定窗口最轻但有临界双倍毛刺，滑动窗口更平滑但 ZSet 会随 QPS 膨胀，漏桶强制匀速、不允许突发。高并发网关先本地限流，再向 Redis 批量申请全局配额，避免把单个限流 key 打成热 key。

- 问：Redis 和 MySQL 怎么保持一致？
  答：默认先写 MySQL，再删 Redis；删失败通过 MQ 重试或订 binlog 补偿，并给缓存设置 TTL 作为最终兜底。这样仍存在短暂旧读和极小的旧值回填窗口，因此缓存只能最终一致；要求读到已提交最新值时，必须直读 MySQL，不要把 Redis 当权威。

- 问：缓存击穿、穿透、雪崩怎么处理？
  答：**结论：**击穿是一个热 key 失效后并发回源，用互斥回填、singleflight 或逻辑过期挡住同一行数据库；穿透是查询本来不存在的数据，用参数校验、空值缓存，假 id 海量时再加布隆过滤器；雪崩是大量 key 同时失效或 Redis 故障，用 TTL 随机打散、预热、高可用和限流降级。三者触发条件、读写路径和边界不同，不能只靠一个布隆过滤器解决。

- 问：多级缓存怎么设计、怎么保持一致？
  答：读按进程本地、Redis、MySQL 向下查并逐层回填，让热点尽量停在本地；写先改 MySQL，再删 Redis，并广播本地失效。各实例本地缓存天然不一致，本地 TTL 要短于 Redis，并以短 TTL 兜住广播丢失；缓存始终不是权威，强一致数据不要依赖本地缓存。

- 问：秒杀怎么防超卖？
  答：先在网关限流、动静分离和验证码削掉无效洪峰；Redis 用 Lua 原子检查库存、预扣并记录已购，MQ 异步建单削峰；数据库以 `stock > 0` 的条件更新和唯一索引保证最终不超卖。预扣成功但消息或落库失败、订单超时未支付都要幂等补偿和对账，Redis 预扣不是最终账本。

## 稳定性与高可用

- 问：主从复制、Sentinel 与 Cluster 是什么关系？
  答：主从复制是保存数据副本的基础机制，本身不自动完成故障转移。Sentinel 是主从部署中的自动故障转移与服务发现方案，不应单独列为与主从复制、Cluster 并列的高可用类别。Cluster 将数据分片到多个主节点，每个分片仍使用主从复制，并由集群内置机制协调故障转移，无需 Sentinel。

- 问：Redis 高可用方案如何选择？
  答：单实例容量和写入能力满足需求时，采用主从部署，通常配合 Sentinel 实现自动故障转移和主节点发现；需要横向扩展容量或分散不同 key 的写入负载时，采用 Cluster，并为各分片配置从节点。Cluster 使用 16384 个哈希槽，客户端需要支持槽路由，跨 key 原子操作通常受同槽条件限制。两种部署都依赖异步复制，故障转移后可能丢失最近已确认写入；高可用不能替代强一致性保证。详细机制见 [Redis 高可用](140-redis高可用.md)。
