# Pipeline、事务、Lua 怎么选

> 本文以 Redis 7.x 为基准；实现细节以 Redis 7.2.0 官方源码核实。

## 0. 问答总结

### 0.1 Pipeline、事务、Lua 怎么选？

1. **Pipeline 只减少 RTT。** 命令仍可被其他客户端插入，不保证原子。
2. **事务保证连续执行。** 适合命令已知且不需要中间结果的批处理；执行错误不回滚。
3. **Lua/Functions 处理读后写。** 脚本在主线程连续运行，也不回滚，必须短小、确定。

### 0.2 Redis 7 的 Functions 和 Lua 有什么关系？

1. **Functions 从 7.0 起提供持久化函数库。** `FUNCTION LOAD` 后用 `FCALL` 调用。
2. **执行语义仍是脚本语义。** 不能阻塞太久，异常不会撤销已完成写入。
3. **脚本或函数访问的 key 在集群中必须同槽。** 跨槽要拆分业务。

## 1. 详细知识点

## 1. Pipeline：省网络，不是事务

**一批互不依赖的命令只求少跑网络，用 Pipeline。广告频控里对多个活动 key 各做一次 `INCR`，彼此无依赖，就该批量发出，不要逐条等回包。**

一次 `INCR rate:api:click_callback:{campaign_id}` 在内存里很快，耗时主要在客户端到 Redis 的往返。十条独立命令逐条发送就是十次 RTT。

```
不开 pipeline
  INCR → 等回包 → INCR → 等回包 → INCR → 等回包

开 pipeline
  INCR INCR INCR 一起发出 → 一起收回
```

服务端仍然按条执行。其他客户端的命令可以插在这两条之间。Pipeline 不保证这批命令必须连着跑完，也不把成功和失败绑在一起。

事务可以和 Pipeline 叠用：`MULTI` 与 `EXEC` 之间那些只返回 `QUEUED` 的命令，也可以放进同一次 pipeline 发出。省下的仍是网络往返；连续执行来自 `EXEC`，不是来自 Pipeline。

一次塞得太多，或中间夹着大 key，回包会在客户端攒成很大一波，主线程写回包也会抖。见 `60-redis为什么不能存大key.md`。

---

## 2. 事务：连续执行，出错继续

**命令在入队前已经定死，只要求执行时中间不插队，并且能接受某条失败后其余继续跑，用事务。不要用 Redis 事务去模仿 MySQL 的回滚。**

适合场景：`stock:sku:10086` 与 `sold:sku:10086` 两步固定写入，不依赖中间读结果。

```
MULTI
  DECR stock:sku:10086
  INCR sold:sku:10086
EXEC
```

入队时 `GET` 还没有结果，因此不能根据库存决定这一笔还扣不扣。这种需求不要硬用事务再在客户端分支。`WATCH` 是乐观锁：监视的 key 在 `EXEC` 前被别人改过，整笔不执行，由调用方重试。命令含义、两种失败、`UNWATCH`、集群同槽限制见 `70-redis事务.md`。

---

## 3. Lua：先读后写，原子判断

**需要先读再决定怎么写，或这几步必须绑在一起做完，用 Lua。默认路径是 `EVAL` / `EVALSHA`；脚本要短、要纯，别把大段业务逻辑塞进 Redis。**

Lua 不是 MySQL 的 undo，也没有 `ROLLBACK`。它和事务一样，在主线程里从头跑到尾，期间不插入其他客户端的命令。多出来的能力是：脚本里可以先 `GET`，再决定下一步；检查不通过就 `return`，后面的写入不会发生。

```
GET stock:sku:10086
        ↓
库存不够     直接 return 0
库存足够     DECR，return 1
```

解锁、延时队列里的「取出并删除」、锁续期，都属于同一类：先确认还是自己的，再修改。拆成两条独立命令，中间可以被别人插队。见 `130-redis分布式锁.md`、`45-排行榜和延时队列.md`。限流多步读写也必须包进 Lua，见 `95-redis分布式限流算法.md`。

### 运行机制与纯函数

脚本在主线程串行执行。`lua-time-limit` 默认约 5 秒；超时之后脚本**仍会跑完**，只是其他客户端会先收到忙错误被拒绝。长脚本或扫一遍大 key，会让整个实例卡住。

脚本必须是**纯函数**：同一份脚本、同一组参数，在主库和从库重放结果要一致。不要在脚本里依赖随机数、本地时钟（除非用 Redis 提供且文档明确可复制的路径）、外部 I/O。主从复制传的是脚本与参数，从库再跑一遍；非确定性会导致主从数据分叉。

Lua 同样不回滚。脚本中途报错，已经执行的命令会留在库里。半成品仍要业务兜底。

### Redis 7.2：`EVAL` / `EVALSHA` 与 `FUNCTION`

| | 形态 | 面试怎么说 |
|---|---|---|
| **`EVAL`** | 每次带脚本体 | 讲清机制时够用 |
| **`EVALSHA`** | 先 `SCRIPT LOAD`，再按 SHA 调 | 少传脚本体，热路径常用 |
| **`FUNCTION` / `FCALL`** | 7.0+ 常驻函数库 | 机制相同：主线程串行、要纯、不回滚；面试先讲 `EVAL` 即可 |

```
EVAL "..." 1 stock:sku:10086
```

脚本里的 key 用 `KEYS[]`，参数用 `ARGV[]`。集群中涉及的 key 必须落在同一槽，要求和事务相同，见 `140-redis高可用.md`。

## 补充：三种工具的边界

| | 解决什么 | 不解决什么 | 核心代价 |
|---|---|---|---|
| **Pipeline** | 减少多次单条命令的网络往返 | 不保证中间不插队，不是原子 | 一次塞太多或夹大 key，回包抖动、客户端缓冲膨胀 |
| **事务** `MULTI`/`EXEC` | 一串已知命令连续执行；可配合 `WATCH` | 不回滚；入队时看不到中间结果 | 执行期单条失败留下半成品；跨 slot 不能用 |
| **Lua** `EVAL`/`EVALSHA` | 读完再决定怎么写；检查不通过就不执行后面的写 | 也不回滚已执行命令；超长脚本堵主线程 | 必须纯函数；超时后脚本仍跑完，期间拒其他命令 |

---

## 对照记

```
Pipeline
  ↓ 解决了 RTT；其他客户端可以插队，不是原子
MULTI / EXEC
  ↓ 解决了连续执行；出错继续，看不见中间结果
+ WATCH
  ↓ 解决了乐观并发；冲突高时客户端空转重试
Lua（EVAL / EVALSHA / FUNCTION）
  ↓ 解决了先读后写的原子判断；也不回滚，长脚本堵主线程
MySQL 事务
  ↓ 才有出错整笔回滚；不要在 Redis 里找同等物
```

一句话：**Pipeline 节省网络，事务是出错后继续执行的批处理，需要先读再决定时用 Lua；三者都不是 MySQL 那种回滚事务，脚本还得短且纯。**
