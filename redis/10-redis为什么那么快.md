# Redis 为什么快：一次请求省下了哪些成本

## 0. 问答总结

### 0.1 Redis 为什么快？

1. **内存访问。** 常规数据读写直接操作内存，减少等待存储设备的时间。
2. **结构合适。** 按业务类型和数据规模选择编码，兼顾空间与操作成本。
3. **高效调度。** I/O 多路复用管理连接，主线程串行执行常规命令，减少共享数据并发协调。

### 0.2 单线程为什么还能处理很多连接？

1. **等待和计算分开。** 事件循环只处理就绪连接，不必为每个连接创建线程。
2. **命令仍然串行。** 连接多不等于命令并行；单条命令越短，主线程越快轮到其他请求。

### 0.3 Redis 的性能瓶颈一定是网络吗？

1. **取决于负载。** CPU、网络、内存、磁盘和操作系统调度都可能成为瓶颈。
2. **先测再改。** 轻命令高流量看网络与 CPU；长命令看执行耗时；持久化期间看 fork、刷盘和内存压力。

### 0.4 怎样让业务真正用得快？

1. **减少往返。** 独立命令可以分批 Pipeline，减少逐条等待网络响应。
2. **控制单次工作量。** 限制集合扫描、脚本时长、value 和回包大小。
3. **按瓶颈扩展。** I/O 线程改善部分网络开销，分片扩展容量和多 key 吞吐，单个热点还需单独治理。

## 1. 先分清命令快与请求快

本文以 Redis 7.x 为基准，线程、对象编码实现核对 **7.2.0**。一次客户端请求耗时可拆为：网络往返、排队、命令执行、回复传输和客户端处理。内存让“命令执行”通常较短，但不保证端到端请求始终低延迟。[1][2]

```mermaid
flowchart LR
    A[客户端发请求] --> B[网络传输]
    B --> C[事件循环处理就绪连接]
    C --> D[主线程执行内存操作]
    D --> E[发送回复]
    E --> F[客户端得到结果]
```

图中任何一段变慢，请求都会变慢。例如前一条 `HGETALL` 正在遍历大 Hash，后面的 `GET` 即使只读几个字节，也要先排队。不能用 `GET` 的理论复杂度解释全部延迟。

## 2. 四个原因，各有适用条件

| 原因 | 为什么有用 | 边界 |
|---|---|---|
| 数据在内存 | 常规查询不需要先从磁盘加载数据页 | AOF、fork、缺页或交换仍可能影响延迟 |
| 合适的数据结构 | Hash 按字段找，ZSet 按分值查；小对象用紧凑编码 | 全量读取仍需遍历并输出全部结果 |
| I/O 多路复用 | 一个事件循环处理许多就绪连接 | 多路复用不是命令并行 |
| 串行命令执行 | 常规数据操作不需要多个执行线程争抢同一数据锁 | 复杂命令能耗尽单核，慢命令会拖累其他请求 |

小 Hash 使用 listpack 时需要顺序查字段；大 Hash 换成哈希表后，按字段查询平均更高效。**大 Hash 并不意味着每条命令都变为 O(N)**，`HGETALL` 的全量遍历与 `HGET` 的单字段定位必须分开。详见[数据类型](30-redis数据类型.md)。[3]

## 3. 优化顺序：从证据选择手段

先看业务延迟和服务器 CPU、网络流量，再结合 `INFO commandstats`、`SLOWLOG GET` 判断命令本身是否昂贵。慢日志主要衡量命令执行，不包含完整的客户端网络等待；慢日志干净不能证明服务器没有排队或网络瓶颈。

若每次请求都在等前一条回复，Pipeline 可以减少往返等待，但需要限制批次大小，避免请求和回复缓冲区膨胀。若主线程忙于长脚本或集合全量遍历，增加 I/O 线程无法替代缩短命令。若一台实例承担太多独立 key，可用分片分担；一个极热 key 不会自动拆到多个分片。[1][2]

**纠正旧表述：**“单核 CPU 很少算不过来”“网络通常一定是大头”都不是通用结论。“内存数据库”也不等于持久化与磁盘从不影响请求。
