# Redis 分布式限流算法

## 0. 问答总结

### 0.1 Redis 分布式限流算法 的核心结论是什么？

1. **先说结论：** 常规网关和开放 API 默认采用 Redis 令牌桶：请求到达时按经过时间补充令牌，再原子判断并扣减；补充、判断、扣减和状态更新应由同一个 Lua 脚本完成。
2. **版本边界：** 本文以 Redis 7.x 为基准；配置、默认值和实现细节以注明的 7.2.0 依据为准。
3. **落地边界：** 方案要结合流量、数据规模和一致性要求验证，不能把经验阈值当成 Redis 保证。

**常规网关和开放 API 默认采用 Redis 令牌桶：请求到达时按经过时间补充令牌，再原子判断并扣减；补充、判断、扣减和状态更新应由同一个 Lua 脚本完成。**

固定窗口适合粗粒度防刷；滑动窗口适合低 QPS 的敏感操作；漏桶适合必须按固定速率调用的脆弱下游。面对超高并发，应先在网关本地过滤，再向 Redis 批量申请全局配额。Lua 原子性见 `75-pipeline事务和lua.md`，热 key 风险见 `65-redis热key.md`。

## 1. 固定窗口：实现最简单，但边界可能放大两倍流量

**适合非核心接口的粗粒度限制，例如同一用户每个自然分钟最多发送 5 条短信。** 常见 key 为 `rate:sms:{uid}:202603102215`，用 `INCR` 计数，并在首次创建时设置过期时间。

`INCR` 和 `EXPIRE` 必须放在同一个 Lua 脚本中：

```lua
local current = redis.call('INCR', KEYS[1])
if current == 1 then
    redis.call('EXPIRE', KEYS[1], tonumber(ARGV[1]))
end
if current > tonumber(ARGV[2]) then
    return 0
end
return 1
```

如果先执行 `INCR`，客户端随后断网或崩溃，`EXPIRE` 可能永远没有执行，计数器会永久存在并持续拒绝请求。

固定窗口的边界存在“临界毛刺”：阈值为每分钟 100 次时，攻击者可以在第 59 秒发送 100 次，再在下一分钟第 1 秒发送 100 次。两个窗口各自未超限，但两秒内实际通过 200 次请求。因此它不适合需要严格平滑流量的核心链路。

## 2. 滑动窗口：消除边界毛刺，但成本随请求数增长

**适合登录失败、验证码等低 QPS 且需要精确统计最近一段时间请求数的场景。** 使用 ZSet 保存请求时间戳，key 例如 `rate:login:ip:{192.168.1.1}`。

每次请求在 Lua 中完成以下步骤：

```text
删除窗口外记录 → 统计窗口内数量 → 未超限则写入当前请求 → 刷新 key TTL
```

`ZADD` 的 member 必须使用请求 ID 或“时间戳 + 请求 ID”等唯一值；如果直接使用可能重复的毫秒时间戳，同一毫秒内的请求会互相覆盖，统计结果就会少算。

示例逻辑：

```lua
local key = KEYS[1]
local now = tonumber(ARGV[1])
local window = tonumber(ARGV[2])
local limit = tonumber(ARGV[3])
local clear_before = now - window

redis.call('ZREMRANGEBYSCORE', key, 0, clear_before)
local count = redis.call('ZCARD', key)
if count < limit then
    redis.call('ZADD', key, now, ARGV[4])
    redis.call('PEXPIRE', key, window)
    return 1
end
return 0
```

每个请求都要在 ZSet 中保存一个元素。限制对象若达到每秒 10,000 次，窗口内就可能累积 10,000 个成员，并持续执行范围删除、统计和插入，内存与 CPU 成本都随 QPS 增长，容易形成大 key。因此不要把它用于高 QPS 主链路。

## 3. 漏桶：固定速率流出，主动牺牲突发能力

**当下游处理能力固定且脆弱时使用漏桶，例如第三方征信接口或低配置数据库。** 漏桶的语义是限制“允许流出的速率”，请求进入桶后由排队消费者按恒定速率处理；桶满时拒绝请求或排队。仅在请求到达时惰性计算水量，只能判断容量和理论流出量，不能凭空让没有后台消费者的请求按固定间隔执行。

Redis 可以只保存漏桶状态，在请求到达时惰性计算：

```text
请求到达
  ↓
按 (now - last_time) × leak_rate 计算已流出的水量
  ↓
water = max(0, water - leaked)
  ↓
water + 1 ≤ capacity？
  ├─ 是：写回 water 和 last_time，交给按速率运行的消费者
  └─ 否：拒绝或进入等待队列
```

状态通常保存在 Hash 中，包括 `last_time` 和 `water`。漏桶的代价是完全不承认瞬时突发：即使下游当时空闲，只要请求到达速度超过漏出速度，也会被拒绝或排队，导致延迟上升。因此它不适合作为通用互联网接口的默认限流算法。

## 4. 令牌桶：兼顾平均速率和合法突发

**令牌桶是网关、开放 API 和回调接口的默认选择。** 桶以固定速率补充令牌，令牌数不超过容量；请求取得令牌后放行。短时间内可以消耗积累的令牌，令牌耗尽后恢复为平均速率。

```text
请求到达
  ↓
按 (now - last_time) × refill_rate 计算新增令牌
  ↓
tokens = min(capacity, tokens + new_tokens)
  ↓
tokens ≥ 1？
  ├─ 是：扣除令牌，更新状态，放行
  └─ 否：拒绝或返回重试时间
```

可选实现有两种：

- 自定义 Lua：在 Redis 单机、主从或集群中保存时间戳和令牌数，不依赖额外模块。
- RedisCell 的 `CL.THROTTLE`：由模块一次完成判断，并返回是否允许、剩余令牌和建议等待时间；代价是需要在 Redis 节点加载扩展。

落地时要处理两个问题：

1. **时间来源。** 如果时间戳由客户端提供，各机器的时钟漂移会造成补充量误差；应统一时间源，并评估 Lua 中使用 Redis `TIME` 对复制和集群环境的影响。
2. **单 key 争抢。** 同一限流 key 的 Lua 操作只能在一个 Redis 分片上串行执行，流量过大时会成为热 key。

## 5. 高并发：本地限流与 Redis 全局配额结合

集中式限流可以共享集群总额度，但每次请求都要增加网络往返，并把压力集中到 Redis。单个热 key 的 Lua 执行能力有限，几十万 QPS 直接访问同一个 key 会堵塞 Redis 主线程。

推荐流程如下：

```text
外部请求
  ↓
网关本地令牌桶：先过滤大部分超额请求
  ↓
本地额度耗尽时，批量向 Redis 申请全局配额
  ↓
Redis 用 Lua 原子扣减，例如一次申请 100 个 token
  ↓
网关在本地消费已租得的额度
```

本地限流消化瞬时流量，Redis 只负责集群级总量控制。批量租约可以显著降低 Redis 请求次数，但会带来额度分配不均和实例故障时少量额度浪费，需要按业务容忍度设置批量大小和租约过期时间。

## 6. 算法对照

| 算法 | 统计方式 | 是否允许突发 | Redis 结构 | 适用场景 | 主要代价 |
|---|---|---|---|---|---|
| **固定窗口** | 固定时间片内计数 | 允许，边界处可能出现两倍毛刺 | String + `INCR` + `EXPIRE` | 粗粒度防刷 | 边界不平滑 |
| **滑动窗口** | 统计最近时间段的真实请求 | 允许，边界平滑 | ZSet 时间戳 | 低 QPS 敏感操作 | 内存和 CPU 随 QPS 增长 |
| **漏桶** | 按固定速率流出 | 不允许或需排队 | Hash/String 保存水量和时间 | 保护固定能力下游 | 突发被拒绝，延迟可能增加 |
| **令牌桶** | 固定速率补充令牌 | 允许至桶容量 | Hash/String 保存令牌和时间 | 网关、API、回调接口 | 实现较复杂，存在热 key |

**记忆方式：**粗粒度防刷用固定窗口；低 QPS 的严格时间窗用滑动窗口；下游必须匀速调用时用漏桶；常规分布式限流默认用令牌桶。无论采用哪种算法，关键判断和状态更新都应由 Lua 原子完成；超大流量再叠加本地限流和 Redis 批量配额。
