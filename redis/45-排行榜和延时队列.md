# 排行榜和延时队列怎么用 ZSet 做

> 本文以 Redis 7.x 为基准；实现细节以 Redis 7.2.0 官方源码核实。

## 0. 问答总结

### 0.1 ZSet 怎样做排行榜？

1. **用 score 存分数，member 存对象 ID。** `ZINCRBY` 改分，`ZREVRANGE` 取高分榜，`ZREVRANK` 查名次。
2. **排名从 0 开始。** 同分默认按 member 字典序，不等于先到先得；需要稳定规则时要额外设计。
3. **别把全量榜一次读出。** 分日榜、赛季榜或只保留 Top N，避免单 key 过大。

### 0.2 ZSet 怎样做延时队列？

1. **score 存到期时间戳，member 存任务 ID。** 消费者取 `score <= now` 的成员。
2. **取出和删除必须原子。** 用 Lua 或合适的弹出命令，避免两个消费者重复拿到同一任务。
3. **弹出即删除没有 ACK。** 消费者宕机可能丢任务；不能丢时用 Stream 或专业 MQ。

## 1. 详细知识点

## 1. 排行榜：改分、取榜、查个人名次

**默认路径就是一个赛季 / 一天一个 ZSet：`ZINCRBY` 改分，`ZREVRANGE` 取 Top N，`ZREVRANK` 查个人名次。只有同分要先到先得、多维分页、日榜合周榜时，再升级 score 编码与 `ZUNIONSTORE`。**

广告创意日榜 key 例如 `leaderboard:ad:{20260206}`，游戏赛季榜例如 `leaderboard:game:{season_1}`。

```
ZINCRBY leaderboard:game:{season_1} 100 player:10086
        ↓
ZREVRANGE leaderboard:game:{season_1} 0 9 WITHSCORES
        ↓ 前十（分高在前）
ZREVRANK leaderboard:game:{season_1} player:10086
        ↓ 0 = 第一名
ZSCORE leaderboard:game:{season_1} player:10086
```

默认小分在前。榜要大的在前用 `ZREV*`。排名从 0 起，别和业务「第 1 名」口头说法搞混。

### 同分并列：把时间掺进 score

ZSet 同分时按 member 字典序决胜，不是先到先得。要「积分高优先，同分先达成者靠前」，把积分和时间压进同一个 double：

```
score = 积分 * 10^10 + (MAX_TIME - 达成时间戳)
```

`10^10` 把积分抬到高位，低位留给时间差。`MAX_TIME - 时间戳` 让更早达成的人低位更大，同积分时排更前。代价是 score 是 double，整数精确只到 2⁵³；积分与时间戳的量级要算过，别把业务 ID 塞进 score。

### 多维度分页

按名次翻页直接 `ZREVRANGE key start stop`。按分数段筛人用 `ZRANGEBYSCORE` / `ZCOUNT`。不要 `ZREVRANGE 0 -1` 一把倒出整榜，那是大 key 读写，见 `60-redis为什么不能存大key.md`。

### 日榜 / 周榜合并

日榜 key 按天切：`leaderboard:ad:{20260201}` … `leaderboard:ad:{20260207}`。周榜用 `ZUNIONSTORE` 合成临时 key，再读 Top N：

```
ZUNIONSTORE leaderboard:ad:week:{2026w36} 7
  leaderboard:ad:{20260201} ... leaderboard:ad:{20260207}
  AGGREGATE SUM
        ↓
ZREVRANGE leaderboard:ad:week:{2026w36} 0 99 WITHSCORES
```

代价：`ZUNIONSTORE` 在主线程里按输入规模干活，日榜过大时合并会堵；结果 key 也要设 TTL，别永久占内存。历史权威榜仍应落 MySQL，Redis 只扛热查询。

### 边界

几千万用户塞进一个 `leaderboard:game:{season_1}` 就是大 key。按赛季 / 天拆；只留前 N，`ZREMRANGEBYRANK` 裁尾。视频热度这类加权分在应用算完再 `ZADD`，Redis 不负责公式。

## 2. 延时队列：score 是到期时间

**默认路径：ZSet 的 score 存到期时间戳，member 存任务 ID；消费者用 Lua 原子「取到期 + 删除」。不要客户端先 `ZRANGEBYSCORE` 再 `ZREM`，中间必有竞态。要 ACK / 消费组时升级到 Stream 或专业 MQ。**

订单 30 分钟未支付取消，key 例如 `delay:order:cancel`，member 为 `order:10086`，详情放 Hash 或 MySQL，别把整单 JSON 塞进 member。

```
现在 = 1730000000
        ↓
ZADD delay:order:cancel 1730001800 order:10086
        ↓ 轮询 / 定时
Lua: ZRANGEBYSCORE 0 now LIMIT 0 100 + 逐条 ZREM
        ↓
拿到 order:10086 → 业务关单
```

### 为什么必须 Lua

`ZRANGEBYSCORE` 只看不删。两个消费者同时看到同一批到期任务，都会去执行；或者 A 看到后崩溃、还没 `ZREM`，B 再看到——重复或丢失取决于你怎么写。出队必须原子：

```lua
local tasks = redis.call('ZRANGEBYSCORE', KEYS[1], 0, ARGV[1], 'LIMIT', 0, tonumber(ARGV[2]))
for i, member in ipairs(tasks) do
    redis.call('ZREM', KEYS[1], member)
end
return tasks
```

也可用 `ZPOPMIN` / `BZPOPMIN`：弹出的一定是当前最小 score，适合「队头到期就处理」的模型；若只要「≤ now」的一批，仍用上面的 score 窗 + Lua。Lua 与原子性见 `75-pipeline事务和lua.md`。

### 消费者挂了会丢消息

Lua / `ZPOPMIN` 出队成功后，任务已从 ZSet 消失。消费者这时宕机，这条延时任务就没了——和 List 的 `BRPOP` 同一类硬伤。边界是：丢了能靠扫库补（例如扫「未支付且超时」订单）的任务，可以只用 ZSet；不能丢的，要「处理中」备份、Stream PEL，或直接上 MQ。

### 和 Stream / MQ 怎么选

| | 排行榜 | 延时队列 |
|---|---|---|
| **score 含义** | 积分 / 热度 / 消耗 | 到期 Unix 时间戳（毫秒或秒） |
| **member** | 玩家 / 创意 / SKU ID | 任务 ID，例如 `order:10086` |
| **核心读法** | `ZREVRANGE` / `ZREVRANK` | `ZRANGEBYSCORE` 到期窗 + 原子出队 |
| **解决什么** | 高频改分与 Top N，不必每次扫 MySQL | 到点触发取消、补发、超时关单 |
| **不解决什么** | 跨天对账权威、亿级全量榜 | ACK、重试、消费组、长期积压 |

| | ZSet 延时 | Stream / MQ |
|---|---|---|
| **擅长** | 按时间排序弹出 | 可靠投递、消费组、重试 |
| **ACK** | 无，弹出即删 | 有 |
| **积压** | 成员过多变大 key | 专为堆积设计（仍有上限） |
| **默认** | 短延时、可补偿的到点任务 | 公司级总线、严格不丢 |

时钟以 Redis 机器为准；成员没有单独 TTL，过期靠你按 score 弹，见 `50-redis过期策略.md`。List 做不了中间先到期：只能死等队头。

## 对照记

```
ZINCRBY + ZREVRANGE + ZREVRANK
  ↓ 单榜够用：改分、Top N、查个人名次
score 掺时间 / ZUNIONSTORE
  ↓ 解决同分先后与多日合并；合并成本随榜变大
ZSet score=到期 + Lua 出队
  ↓ 到点触发；无 ACK，消费者挂了可能丢
Stream / 专业 MQ
  ↓ 要消费组与可靠投递时再升级
```

一句话：**排行榜和延时队列都是 ZSet；榜用分值排序，队用时间戳弹出。出队必须原子，榜要拆 key 防大 key；要 ACK 就别只靠 ZSet。**
