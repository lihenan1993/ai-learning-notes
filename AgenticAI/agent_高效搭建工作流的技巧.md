# 高效搭建工作流的技巧

搭建智能体工作流时，不必一开始就追求完整和复杂。更高效的方法是先做出一个能够运行的粗糙版本，再用小规模评估发现问题，通过连续迭代逐步提高质量。

## 1. 先搭建粗糙但可运行的 Agent

先实现最小可行工作流，让 Agent 能够从输入任务走到最终输出。初版可以暂时使用简单的提示词、较少的工具和较短的流程，重点是尽快获得真实运行结果。

初版工作流至少应具备：

- 明确的输入和输出；
- 能够完成核心任务的最少步骤；
- 必要的工具调用或数据来源；
- 可以记录最终输出和关键中间结果。

此时不应过早优化所有边界情况。没有真实输出，就无法判断哪些问题真正值得解决。

## 2. 用小规模 Eval 快速评估

为初版 Agent 准备一组规模较小、但能代表主要场景的评估样本。先通过这组样本快速了解工作流的基本表现，并记录具体失败案例。

小规模 Eval 可以优先检查：

- 是否完成了用户的核心目标；
- 输出格式是否符合要求；
- 是否出现明显的事实错误或遗漏；
- 工具是否被正确选择和调用；
- 运行耗时、调用次数和成本是否可接受。

评估结果应尽量包含失败样本和错误原因，而不只是一个总分。具体错误比抽象分数更容易指导下一轮修改。

## 3. 根据结果迭代工作流

根据 Eval 暴露的问题，针对性修改 Agent 的提示词、模型、工具、上下文、步骤顺序或异常处理逻辑。每轮修改尽量聚焦一类问题，并保留修改前后的评估结果，便于判断改动是否有效。

可以按以下顺序排查：

1. 任务理解是否正确；
2. 规划或步骤拆分是否合理；
3. 工具选择和参数是否正确；
4. 中间结果是否被正确理解和传递；
5. 最终输出是否满足格式和质量要求。

## 4. 让 Eval 随工作流一起成长

Eval 不是固定不变的测试集。每次发现重要问题，都应把对应输入和期望行为加入评估集，避免后续修改再次引入同类错误。

随着工作流变复杂，可以逐步：

- 扩大评估样本集，覆盖更多真实场景和边界情况；
- 增加客观评估规则，检查字段、格式、数值和工具调用；
- 增加 LLM 评估，判断相关性、完整性、表达质量等主观指标；
- 增加组件评估，单独检查规划、检索、工具调用和总结等环节；
- 增加耗时、调用次数和成本等工程指标。

## 5. 循环往复，迭代前进

高效搭建 Agent 的核心不是一次性设计出完美架构，而是建立稳定的反馈循环：

```text
搭建粗糙 Agent
  → 用小规模 Eval 评估
  → 分析失败样本和错误原因
  → 修改 Agent 工作流
  → 将新问题反馈到 Eval
  → 扩大样本集或增加评估方式
  → 重新运行并比较结果
```

这个循环持续进行，工作流和评估能力会同步完善。每一轮迭代都应回答两个问题：Agent 是否变得更好，以及 Eval 是否更能发现真实问题。

## 6. 实践原则

- **先可运行，再求完善**：优先验证核心流程是否成立。
- **用数据代替感觉**：通过样本、指标和失败案例判断改动效果。
- **问题驱动迭代**：围绕真实错误修改工作流，不做无依据的复杂化。
- **评估与开发同步演进**：把新发现的问题沉淀为新的样本或指标。
- **保留回归检查**：每轮修改都重新运行已有 Eval，确认旧功能没有退化。

## 7. 确定表现不佳的组件

当 Agent 的最终结果不好时，不能仅凭直觉判断是哪一个组件出了问题。以研究型 Agent 为例，答案中的要点找得不好，可能来自搜索词生成、搜索结果质量、来源筛选或最终写作推理等多个环节。找对需要改进的组件，通常比盲目修改整个工作流收益更大。

### 7.1 先做错误分析，再修改组件

优先分析出错的案例，而不是花大量时间检查已经表现良好的案例。对每个失败样本查看完整 trace，即每个步骤的中间输出（span），逐步判断：

- 搜索词是否准确、具体；
- 搜索结果是否相关、权威；
- 选出的来源是否覆盖了关键内容；
- 工具返回的内容是否被正确解析；
- 最终写作或推理是否正确使用了已有资料。

例如研究型 Agent 的典型流程是：

```text
用户问题
  → LLM 生成搜索词
  → 网页搜索
  → LLM 选择最佳来源
  → 抓取网页或 PDF 转文本
  → LLM 撰写答案
```

最终答案错误时，应沿着这个顺序检查每个 span，定位错误首次出现的位置。若搜索词已经合理，但搜索结果质量很差，问题可能在搜索工具或检索配置；若来源质量足够而答案仍然错误，则更可能是来源选择、内容理解或最终写作环节的问题。

### 7.2 建立错误分析表

把失败样本按组件记录下来，统计每个组件造成或放大错误的次数。表格中的“问题描述”应写具体事实，例如“搜索结果包含过多博客，缺少论文”，而不是笼统地写“检索不好”。

| 用户问题 | 搜索词生成 | 搜索结果 | 来源选择 | 最终写作 | 主要责任组件 |
| --- | --- | --- | --- | --- | --- |
| 黑洞科学的最新进展 |  | 博客过多，论文不足 |  |  | 搜索结果 |
| 西雅图租房还是买房 |  |  | 漏掉知名博客 |  | 来源选择 |
| 用机器人采摘水果 | 关键词过于泛化 | 返回面向小学生的网站 |  |  | 搜索词生成 |
| 电动汽车电池 |  | 只选了美国公司 | 漏掉重要杂志 |  | 搜索结果、来源选择 |

可以在表格下方汇总比例：

| 组件 | 负责的错误数 | 占全部错误比例 | 优先级 |
| --- | ---: | ---: | --- |
| 搜索词生成 |  |  |  |
| 搜索结果 |  |  |  |
| 来源选择 |  |  |  |
| 最终写作 |  |  |  |

### 7.3 按影响优先处理

优先修改错误比例高、影响范围大的组件。单个案例中偶然出现的问题不一定值得立即处理；如果多个失败样本都在同一个 span 首次出现错误，就应优先为该组件设计改进方案，并增加针对性的 Eval。

定位完成后，再回到“修改工作流 → 重新评估 → 记录新错误”的循环，验证改动是否真正降低了该组件的错误率，同时确认没有引入新的回归问题。

## 8. 进行组件级评估

当某个组件表现不佳时，应先把它从整个工作流中单独抽出来评估。例如需要替换 Web Search 工具时，如果每次都重跑完整的端到端评估，成本可能很高；其他组件的随机性和噪声也可能掩盖 Web Search 本身的变化，使结果难以解释。

### 8.1 建立组件的黄金标准

为每个代表性问题整理一组权威、相关的网页，作为该问题的黄金标准结果集（gold-standard set）。结果集可以由领域专家筛选，也可以结合可信来源、人工复核和去重得到。

对于 Web Search，评估数据至少应包含：

- 用户问题或搜索任务；
- 期望命中的权威网页 URL；
- 网页的主题、来源类型或质量标签；
- 可接受的同义页面或替代来源（如果存在）。

黄金标准不一定要求搜索结果与指定 URL 完全一致，也可以按域名、页面主题、来源等级或人工标注的相关性进行匹配。

### 8.2 用代码评估搜索结果

固定搜索任务和黄金标准后，直接调用候选 Web Search，使用代码统计结果中命中黄金标准的数量和位置。常用指标包括：

- 命中率：结果中是否至少包含一个黄金标准网页；
- 召回率：黄金标准网页中有多少被搜索结果找回；
- `Precision@K`：前 K 个结果中有多少属于黄金标准；
- `Recall@K`：前 K 个结果覆盖了多少黄金标准；
- 平均排名：黄金标准网页在结果中的平均位置。

一个简单的评估过程是：

```text
读取搜索任务和黄金标准结果集
  → 调用 Web Search
  → 规范化 URL 并去重
  → 与黄金标准集合匹配
  → 计算命中率、Recall@K 和平均排名
  → 对比不同搜索配置或工具版本
```

### 8.3 比较组件改动

在保持搜索任务、黄金标准和评估代码不变的情况下，逐项调整 Web Search 的实现或参数，例如替换搜索服务、改变返回数量、增加域名过滤、调整排序方式或修改查询词生成策略。记录每次改动前后的组件指标：

| 配置 | 返回数量 K | 命中率 | Recall@K | 平均排名 | 成本或耗时 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 原 Web Search |  |  |  |  |  |
| 候选 Web Search |  |  |  |  |  |
| 候选配置 A |  |  |  |  |  |
| 候选配置 B |  |  |  |  |  |

组件指标有提升时，说明该组件更可能满足预期；但这还不能证明整个 Agent 的最终答案一定变好，因为后续来源选择、内容抓取和写作环节仍可能产生错误。

### 8.4 最后进行端到端验证

组件级评估筛选出更好的工具或参数后，再运行一段时间的端到端 Eval，观察最终任务成功率、答案质量、耗时和成本是否同步改善。端到端验证应使用固定的对照版本和相同的任务集，并保留足够样本，避免一次运行的随机结果造成误判。

```text
组件级评估筛选候选方案
  → 选定改动并接入完整工作流
  → 运行一段时间的端到端 Eval
  → 比较最终质量、稳定性、耗时和成本
  → 确认改动是否值得保留
```

组件级指标用于快速定位和筛选，端到端指标用于确认真实系统收益。两者应配合使用，不能只根据其中一种评估结果做结论。

## 9. 改进组件表现的方法

定位到问题组件后，应根据组件类型选择改进方法。LLM 组件和非 LLM 组件的优化手段不同，但都应通过 Eval 验证，而不是只凭主观感觉判断。

### 9.1 改进 LLM 组件

对于负责规划、搜索词生成、来源选择、总结或写作的 LLM 组件，可以依次尝试：

- **改进提示词**：增加更明确的任务说明、约束条件、输出格式和失败处理要求；
- **加入具体示例**：在提示词中加入一个或多个高质量输入输出示例，使用少样本提示（few-shot prompting）；
- **更换模型**：用多个候选 LLM 在同一组 Eval 上比较，选择质量、速度和成本更合适的模型；
- **拆分步骤**：将一个过于复杂的步骤分解成多个更小、更容易评估的步骤；
- **微调模型**：当有足够的内部高质量数据和稳定任务模式时，使用领域数据微调模型。

每次只改变少量变量，并保留同一套评估样本，才能判断改进是否来自当前调整。

### 9.2 改进非 LLM 组件

非 LLM 组件包括 Web Search、RAG 检索、代码执行器以及语音识别、目标检测等训练好的机器学习模型。常用方法包括：

- **调整组件超参数**：例如改变 Web Search 返回结果数量和日期范围，调整 RAG 的相似度阈值与文本块大小，或修改机器学习模型的检测阈值；
- **替换组件实现**：尝试其他搜索引擎、RAG 提供商、嵌入模型或机器学习模型；
- **使用组件级 Eval 筛选方案**：先在黄金标准数据集上比较组件指标，再接入完整工作流做端到端验证。

超参数调整应采用可记录、可复现的实验方式，避免同时修改多个参数导致结果无法解释。

## 10. 培养对模型能力的直觉

模型的实际能力会因任务类型、提示词、上下文长度和输出约束而变化。持续建立对模型的直觉，有助于更快选择合适的模型和工作流设计。

可以通过以下方式积累经验：

- 经常用一组个人 Eval 试用不同模型，记录它们在推理、检索、结构化输出、写作和工具调用任务上的差异；
- 阅读其他人的提示词和工作流设计，从中发现模型更容易理解的任务表达方式；
- 在同一个 Agent 工作流中为不同步骤尝试不同模型，比较哪类模型适合规划、工具调用、总结或最终回答；
- 使用支持快速切换模型的接口或抽象层，降低比较和替换成本。

模型直觉不能替代正式评估，但可以帮助缩小候选方案范围。最终仍应以组件级和端到端 Eval 的结果决定是否采用某种模型或配置。

## 11. 优化成本和延迟

优化成本和延迟应建立在高质量结果已经稳定的基础上。先确保 Agent 能持续完成目标、输出质量达到要求，再优化运行效率；如果过早追求便宜或快速，可能会牺牲系统性能和用户价值。

### 11.1 先测量，再优化延迟

对完整工作流做基准测试（benchmark），记录从收到用户请求到返回最终结果的总延迟，并拆分每个步骤的耗时。以研究型 Agent 为例，可以分别记录生成搜索词、Web Search、来源筛选、网页抓取、PDF 转文本和最终写作的耗时。

```text
用户请求
  → 搜索词生成：7s
  → Web Search：5s
  → 来源筛选：3s
  → 网页抓取：11s
  → 最终写作：18s
```

基准测试应使用固定任务集并重复运行多次，记录平均值、P50 和 P95 延迟，而不是只看一次运行结果。先找出占用时间最多的步骤，再评估并行执行、缓存、减少返回内容、替换更快的模型或工具等优化方式。

| 步骤 | 平均耗时 | P95 耗时 | 占总延迟比例 | 优化候选 |
| --- | ---: | ---: | ---: | --- |
| 搜索词生成 |  |  |  |  |
| Web Search |  |  |  |  |
| 来源筛选 |  |  |  |  |
| 网页抓取或 PDF 转文本 |  |  |  |  |
| 最终写作 |  |  |  |  |

优化后必须重新运行相同基准测试，并同时检查质量指标，确认延迟下降没有造成答案质量退化。

### 11.2 计算工作流成本

先研究每种组件的计费方式，再统计每个步骤的平均花费。常见成本来源包括：

- **LLM 步骤**：按输入和输出 token 计费；
- **API 工具**：按 API 调用次数计费；
- **计算步骤**：根据服务器规格、运行时间或计算资源使用量计费。

记录每个 span 的输入 token、输出 token、调用次数、单价和单次成本，再汇总为单个任务的总成本。不同供应商的计费单位和阶梯价格可能不同，成本表应标明价格版本和统计时间。

| 步骤 | 计费方式 | 平均用量 | 单价 | 单次平均成本 |
| --- | --- | ---: | ---: | ---: |

| Web Search | API 调用 |  |  |  |

| 网页抓取或 PDF 转文本 | API 调用或计算资源 |  |  |  |
| 最终写作 LLM | 输入/输出 token |  |  |  |
| **总计** |  |  |  |  |

### 11.3 按贡献度优化

优先处理成本最高或调用最频繁的步骤，例如减少重复的 LLM 调用、压缩不必要的上下文、缓存稳定结果、限制检索和抓取数量，或为简单步骤选择成本更低的模型。每次改动都应重新测量成本、延迟和质量，保留对照版本，避免只优化单一指标。

```text
稳定高质量结果
  → 基准测试延迟和成本
  → 定位最慢、最贵的步骤
  → 调整参数、缓存、并行化或替换组件
  → 重新运行 Eval 和基准测试
  → 确认质量、延迟和成本的综合收益
```
