# Kafka幂等生产者与事务

Kafka 的幂等生产者和事务都用于提高消息处理可靠性，但解决的问题不同：幂等生产者主要防止生产端因重试造成重复消息；事务用于保证多个 Kafka 操作的原子性，并支持“消费消息、处理业务、生产新消息、提交 offset”这一整组操作的一致性。

## 一 幂等生产者

### 1. 是什么

幂等生产者通过生产者 ID（PID）、分区序列号等机制，让 Broker 能识别并丢弃同一生产者会话中的重复请求。生产者发送成功但未收到响应时，重试不会在同一分区产生重复记录。

幂等性只覆盖 Kafka 生产端，不能保证消费者业务执行幂等，也不能防止业务代码主动发送的重复事件。

### 2. 解决什么问题

典型场景是：生产者已把消息写入 Kafka，但响应因网络抖动丢失；生产者认为发送失败并重试，可能产生两条相同消息。启用幂等生产者后，Broker 会识别重复序列号，最终只保留一条。

### 3. 关键参数

```properties
enable.idempotence=true
acks=all
retries=较大值
max.in.flight.requests.per.connection<=5
```

- `enable.idempotence=true`：开启幂等生产。
- `acks=all`：等待 ISR 中的同步副本确认，通常与幂等生产一起使用。
- `retries`：发送失败时允许重试。幂等性不代表可以关闭重试。
- `max.in.flight.requests.per.connection`：开启幂等时应不大于 5，以保证顺序和协议约束。

较新的 Kafka 客户端在显式开启幂等后会自动调整部分依赖参数；如果参数之间互相矛盾，客户端可能拒绝启动或报配置错误，应以所用客户端版本文档为准。

### 4. 优点

- 降低网络重试造成的重复消息。
- 对业务代码侵入小，通常只需配置参数。
- 性能和吞吐量通常优于事务，适合大多数普通消息生产场景。
- 可以与消息顺序保证、`acks=all` 和重试机制配合使用。

### 5. 局限与缺点

- 主要保证单个生产者会话内、单个分区写入的去重效果，不能替代业务幂等。
- 不能保证数据库更新和 Kafka 发送之间的原子性。
- 生产者重启、业务重复执行或上游重复请求，仍可能产生业务层重复消息。
- 开启 `acks=all` 和重试会增加延迟，并可能降低吞吐量。

## 二 Kafka事务

### 1. 是什么

Kafka 事务允许生产者把多个分区、多个主题的写入放进一个原子操作中，并将消费位移作为事务的一部分提交。事务提交后，消费者才能看到事务消息；事务中止后，这些消息对 `read_committed` 消费者不可见。

### 2. 解决什么问题

事务主要解决以下一致性问题：

- 多个分区或多个主题需要“全部成功或全部失败”。
- Kafka 流程中需要同时完成“消费消息、生产结果消息、提交消费 offset”。
- 避免下游看到未完成或已回滚的中间结果。

例如，订单主题消费成功后要同时写入库存主题和支付主题。使用事务可以避免只写成功其中一个主题。

### 3. 关键参数

生产者：

```properties
enable.idempotence=true
transactional.id=order-service-instance-001
acks=all
```

消费者：

```properties
isolation.level=read_committed
enable.auto.commit=false
```

服务端常见相关参数：

```properties
transaction.state.log.replication.factor=3
transaction.state.log.min.isr=2
transaction.timeout.ms=900000
```

- `transactional.id`：事务生产者的稳定唯一标识。同一时间不能有两个实例使用同一个 ID，否则旧实例会被 fencing（隔离）。
- `isolation.level=read_committed`：只读取已提交事务消息；`read_uncommitted` 会读取未提交或已中止消息。
- `transaction.timeout.ms`：事务超时时间。客户端的 `transaction.timeout.ms` 不能超过 Broker 的 `transaction.max.timeout.ms`。
- 事务状态存储在内部主题 `__transaction_state` 中，因此该主题也需要可靠的副本配置。

### 4. 基本使用流程

```java
producer.initTransactions();
producer.beginTransaction();
try {
    ConsumerRecords<String, String> records = consumer.poll(Duration.ofSeconds(1));
    // 处理 records，并发送结果消息
    producer.send(resultRecord);
    producer.sendOffsetsToTransaction(offsets, consumerGroupMetadata);
    producer.commitTransaction();
} catch (Exception e) {
    producer.abortTransaction();
}
```

实际项目还应处理超时、重试、不可恢复异常和消费者重平衡等情况。

### 5. 优点

- 支持跨分区、跨主题的原子写入。
- 支持 Kafka 的“消费-处理-生产”端到端恰好一次语义（EOS）。
- 事务中止后，`read_committed` 消费者不会看到中间结果。
- 可以把 offset 提交纳入同一事务，减少重复处理和结果消息不一致。

### 6. 缺点

- 配置和代码复杂度明显高于单纯幂等生产。
- 事务需要协调、提交和状态维护，会增加延迟并降低吞吐量。
- 事务长时间未提交可能阻塞 `read_committed` 消费者读取后续消息。
- 事务只能覆盖 Kafka 内部操作，不能自动保证 Kafka 与 MySQL、Redis、HTTP 调用等外部系统的原子性。
- `transactional.id` 管理不当会导致实例互相 fencing；事务超时、重平衡和异常处理也需要额外运维能力。

## 三 幂等生产者与事务的关系

| 对比项 | 幂等生产者 | Kafka事务 |
|---|---|---|
| 核心目标 | 防止生产重试造成重复写入 | 保证一组 Kafka 操作原子提交 |
| 覆盖范围 | 生产者写入，重点是单分区 | 多分区、多主题及消费 offset |
| 是否需要 `transactional.id` | 不需要 | 需要稳定且唯一的 ID |
| 消费者要求 | 普通消费即可，但业务仍需幂等 | 建议 `read_committed` |
| 性能影响 | 较小 | 通常更大 |
| 适用场景 | 普通可靠消息发送 | Kafka 内部的复杂工作流和 EOS |

事务生产者本身依赖幂等机制，因此开启事务时通常也会启用 `enable.idempotence=true`。如果只是担心生产者网络重试导致重复消息，使用幂等生产者即可；只有在需要多个 Kafka 操作原子化，或需要 Kafka Streams/消费-生产恰好一次语义时，才应引入事务。


## 五 新版本差异说明

> Kafka 参数行为会受到 Broker 版本和客户端版本共同影响。以下说明以 Apache Kafka 2.5 及之后的常见客户端行为为主，使用时应核对实际版本文档。

- **幂等生产者默认值变化**：Kafka 3.0 起，Java Producer 的 `enable.idempotence` 默认值为 `true`（前提是没有设置互相冲突的 `acks`、`retries` 或 `max.in.flight.requests.per.connection`）。旧版本通常需要显式设置为 `true`。
- **幂等配置校验**：较新客户端会自动补齐幂等生产所需的 `acks=all`、重试和请求数限制；如果显式配置冲突值，客户端会直接报配置异常，而不是静默降级。生产环境建议显式写出关键参数，避免升级后行为不清晰。
- **事务依赖幂等生产**：新版本中事务生产者必须启用幂等性，客户端会自动设置或校验 `enable.idempotence=true`。不要尝试关闭该配置来“提升性能”。
- **事务协议与 EOS**：较新的客户端和 Kafka Streams 支持更完善的 Exactly-Once Semantics（EOS）能力。`processing.guarantee=exactly_once_v2` 使用新版事务协议，通常优于旧的 `exactly_once`；该配置主要适用于 Kafka Streams，普通 Producer 仍需手动调用事务 API。
- **消费者组协议变化**：Kafka 4.0 引入新的消费者组协议（`group.protocol=consumer`），部分心跳和会话参数由 Broker 管理；旧客户端仍使用经典协议。升级时应确认客户端、Broker 及相关参数是否兼容。
- **事务超时与稳定性**：新版本仍要求客户端事务超时不超过 Broker 的 `transaction.max.timeout.ms`。事务超时时间过长会延迟中止事务和释放资源，不能简单通过调大超时解决业务处理过慢问题。

### 版本标注建议

在项目配置或运维文档中同时记录以下信息：

1. Kafka Broker 版本。
2. Java 客户端版本（`kafka-clients`）。
3. 是否使用 Kafka Streams，以及 `processing.guarantee` 配置。
4. 消费者使用的隔离级别和消费者组协议。

- **普通事件、日志、通知消息**：优先使用幂等生产者、`acks=all`、重试和业务幂等。
- **消费一个主题后生产另一个主题**：如果要求结果消息和 offset 一致，考虑 Kafka 事务。
- **Kafka 与数据库同时更新**：Kafka 事务无法直接覆盖数据库，应结合 Outbox、CDC、可靠消息表或补偿对账方案。
- **高吞吐低延迟场景**：谨慎使用长事务，优先评估幂等生产、至少一次消费和业务去重是否已经满足需求。
