# Kafka 的 Topic、分区、副本和消费者是怎样协作的

**Kafka 是一个高性能的分布式发布与订阅系统。生产者把消息写入 Topic 的分区，Broker 集群保存分区及其副本，消费者通过订阅和拉取读取消息。分区提供并行能力，副本提供故障恢复能力，消费者组支持业务之间独立消费、业务内部共同分担负载；代价是顺序范围、复制开销和消费进度都需要明确管理。**

本文按 Kafka 4.x 整理，优先对照《跟老卫学 Apache Kafka 开发》的主题目录，并用对应版本官方文档核对行为。旧版 ZooKeeper 流程不作为当前架构描述；来源及访问限制见 [笔记导航与参考](kafka-笔记导航与参考.md)。

## 一条订单消息怎样流转

电商系统创建订单后，把订单事件写入 `order-events`。库存服务需要扣减库存，风控服务需要检查风险，两者分别使用自己的消费者组读取同一批事件。

```text
订单服务 Producer
    ↓ 发送 key=order:10086 的订单事件
Topic：order-events
    ↓ 按分区策略选择分区，例如 P1
Broker 2 上的 P1 Leader
    ↓ 追加日志；其他 Broker 上的 P1 Follower 拉取并复制
P1 中形成有序的消息记录，例如 offset=205
    ↓ 两个消费者组分别发起拉取请求
inventory-service 组        risk-service 组
    ↓                          ↓
处理库存事件                处理风控事件
    ↓                          ↓
各自提交消费进度，互不影响
```

Producer 不需要知道哪些 Consumer 会消费消息。消息被消费后通常不会立即删除，而是按 Topic 的保留或压缩策略清理，因此多个业务可以独立读取，也可以在数据仍保留时重新消费。

## 核心概念分别负责什么

| 概念 | 是什么 | 解决什么问题或需要注意什么 |
|---|---|---|
| 消息 / Record | 写入 Kafka 的一条记录，通常包含 key、value、时间戳和可选 headers | value 承载业务事件；key 常用于分区选择 |
| Topic（主题） | 一类消息的逻辑名称，例如 `order-events` | 隔离业务数据和配置；一个 Topic 包含一个或多个分区 |
| Partition（分区） | Topic 的一个有序日志分片 | 提供存储与消费的并行能力；顺序只在分区内成立 |
| Offset（偏移量） | 一条记录在分区内的位置编号 | 定位消息和记录进度；不同分区的 offset 不能比较先后 |
| Replica（副本） | 同一个分区在不同 Broker 上保存的数据拷贝 | 提供冗余，不增加这个 Topic 的逻辑分区数 |
| Broker | Kafka 中负责消息存储和读写请求的服务进程 | 一个 Broker 可以承载多个 Topic 的多个分区副本，不等同于一台物理机器 |
| Cluster（集群） | 协同工作的 Kafka 节点整体 | 分摊负载和支持故障恢复；单节点也可用于开发，但没有跨节点冗余 |
| Producer（生产者） | 向 Topic 发送记录的客户端 | 决定写入内容，并通过分区策略、批量和确认配置影响行为 |
| Consumer（消费者） | 从分区拉取记录并处理的客户端 | 处理业务并维护消费位置；处理成功和提交进度是两个动作 |
| Subscription（订阅） | Consumer 声明自己要读取哪些 Topic | 普通消费者可按名称或正则表达式订阅；订阅不代表 Broker 主动推送消息 |
| Consumer Group（消费者组） | 以相同 `group.id` 协同消费的一组 Consumer | 在组内分配分区，在组间保持独立进度 |
| Controller（控制器） | 管理集群元数据和分区领导权的角色 | 协调节点变化和分区 Leader 选举，不是所有业务消息都要经过的入口 |
| KRaft | Kafka 内置的、基于 Raft 的元数据管理机制 | 替代 ZooKeeper，由 Controller quorum 管理元数据 |

## Topic、分区和副本有什么区别

### Topic 是逻辑分类，分区是实际保存消息的日志

创建 `order-events` 时，可以配置 3 个分区：P0、P1、P2。每个分区拥有自己的日志和 offset 序列；例如 P0 的 offset=205 与 P1 的 offset=205 是两条不同位置的记录。

**Kafka 保证的是分区内日志的顺序，不保证 Topic 跨分区的全局顺序。需要同一订单的事件有序时，通常使用订单 ID 作为 key，让相关消息进入同一分区，同时约束生产端重试和消费端处理方式。**

在分区数和分区策略稳定时，相同 key 通常会进入同一个分区。如果增加分区，默认基于 key 的映射可能改变，历史记录不会自动重新分布。应用还需避免消费者把同一分区的消息交给无序并行任务，否则日志有序也不代表业务完成顺序有序。

分区越多，通常越容易分摊到多个 Broker 和 Consumer，但也会增加日志文件、复制、元数据及分区调度成本。严格要求整个 Topic 全局有序时可以考虑单分区，但会限制并行吞吐。

### 副本是同一份分区数据的冗余

假设 `order-events` 有 3 个分区，副本因子为 3，集群中有 3 个 Broker。副本因子包含 Leader，因此总共有 9 份分区副本，而不是 9 个逻辑分区。

| 分区 | Broker 1 | Broker 2 | Broker 3 |
|---|---|---|---|
| P0 | Leader | Follower | Follower |
| P1 | Follower | Leader | Follower |
| P2 | Follower | Follower | Leader |

同一个分区的副本分布在不同 Broker 上，一个 Broker 可以同时是 P0 的 Leader 和 P1 的 Follower。因此，不能把整个集群简单理解成“一台主节点带多台从节点”。

正常情况下，Producer 向分区 Leader 写入，Consumer 默认从 Leader 读取；Follower 主动向 Leader 拉取数据完成复制。Kafka 也支持在特定配置下从 Follower 读取，基础读写流程按默认行为理解即可。

### 副本不等于绝对不丢消息

ISR（In-Sync Replicas）是与 Leader 保持同步的副本集合，包含 Leader；不表示每一瞬间日志末尾都相同。常规选举优先从 ISR 选择副本。Kafka 4.x 引入合格领导者副本（ELR），4.1 新建集群默认启用：ISR 为空时也可从被跟踪的安全候选中选举，不能与任意落后副本的非干净选举混同。

可靠性还取决于写入确认条件。例如副本因子为 3、`acks=all`、`min.insync.replicas=2` 时，写入要求 ISR 至少有 2 个副本，并等待当前 ISR 满足复制确认条件；`min.insync.replicas` 是允许写入的最低门槛，不是只等待固定 2 个副本。

只剩 1 个同步副本时，这组配置会拒绝写入，以牺牲可用性保护可靠性。`acks=all` 也不等于每个副本都已对每条消息执行磁盘强制刷盘。如果允许落后的非 ISR 副本接任 Leader，即非干净选举，则可能丢失数据。

## 生产者如何找到要写入的 Broker

Producer 配置的 `bootstrap.servers` 是发现集群的入口。客户端连接入口节点获取 Topic、分区和 Leader 的元数据后，会直接向目标分区 Leader 所在的 Broker 发送请求，不要求入口 Broker 转发所有消息。

生产者可以显式指定分区，也可以交给分区器选择。带 key 的记录通常按 key 映射到分区；不带 key 时使用客户端的默认策略，具体策略随版本变化，不应统一描述为逐条轮询。

Producer 通常会按目标分区积累批次后发送，以减少网络和存储开销。写入确认表示满足了对应的 Broker 确认条件，不能说明库存服务已经处理成功。重试也可能造成重复写入，需要结合幂等生产者等机制控制；端到端业务是否重复，还取决于消费端处理。

## 消费者、订阅和消费者组如何配合

### 订阅声明范围，分区分配决定实际任务

以 Java Consumer API 为例，调用 `subscribe` 后参与组分配，通过 `poll` 获取记录。Sarama 使用 `ConsumerGroup.Consume` 和 `ConsumeClaim` 消息通道，不提供同名 poll 调用。长轮询允许服务端在暂无数据时等待再响应，但仍由客户端发起请求。

Java Consumer 也可以用 `assign` 手动指定分区；Sarama 可使用底层 `ConsumePartition`。手动分配不参与自动消费者组分配，需要应用管理分区归属。

### 同组分担任务，不同组独立消费

**在普通消费者组的分区分配模型中，一个分区同一时刻只分配给组内一个 Consumer，一个 Consumer 可以负责多个分区；不同消费者组可以分别消费同一个分区，互不分摊对方的任务。**

以 3 个分区为例：

| 消费者组 | Consumer 数量 | 可能的分配结果 |
|---|---|---|
| `inventory-service` | 2 | 一个处理 P0、P1，另一个处理 P2 |
| `risk-service` | 3 | 每个 Consumer 处理一个分区 |
| `audit-service` | 4 | 3 个 Consumer 分别处理一个分区，1 个空闲 |

上述空闲结论以组内只订阅这个 Topic 为前提；订阅多个 Topic 时，应看所有可分配分区。该限制针对传统消费者组；Kafka 4.2 起生产就绪的共享组允许消费者数量超过分区数。

组内成员加入、离开或订阅的分区数量变化，可能触发 Rebalance，重新分配任务。分配切换可能影响处理延迟，也可能使未提交进度的消息被重新读取。因此，增加 Consumer 的收益受分区数量限制，还会带来协调成本。

### 消费进度与消息保留相互独立

Consumer 当前读取位置与已提交 offset 是不同概念。通常提交的是“下一条要读取的位置”：假设 P1 的 offset=205 已处理成功，可提交 206；组的提交记录一般保存在内部 Topic `__consumer_offsets` 中。

| 执行顺序和故障窗口 | 可能结果 |
|---|---|
| 先提交 206，再处理 205，处理前宕机 | 重启从 206 继续，205 的业务处理可能被跳过 |
| 先处理 205，再提交 206，提交前宕机 | 重启可能再次读取 205，业务可能重复执行 |

对于不能遗漏的业务，常用“处理成功后提交进度，并让业务操作幂等”的方式，但具体提交时机仍需与批次、异步处理和失败重试配合。自动提交不等于自动确认业务成功。

消费进度不会阻止 Kafka 按保留策略删除旧日志。如果积压时间超过保留范围，尚未消费的数据也可能被删除。重置 offset 只能重读仍然存在的数据；日志压缩 Topic 还可能清除同 key 的旧版本，不应当作完整事件历史使用。

## 集群如何通过 KRaft 管理元数据

### Broker 管数据，Controller 管集群状态

集群元数据包括 Topic、分区、副本分配和 Leader 等信息。客户端需要这些信息找到数据位置，集群也需要通过它们处理 Broker 上下线和 Leader 切换。

在旧的 ZooKeeper 模式中，ZooKeeper 保存协调信息并支持 Controller 选举，由选出的 Kafka Controller 协调分区 Leader 选举等工作。不能把它理解成每一条业务消息都经过 ZooKeeper。

**KRaft 使用 Kafka 自己的 Controller quorum 管理元数据，消除了对 ZooKeeper 的依赖。Raft 在这里负责元数据日志的一致性；业务 Topic 的数据仍由分区 Leader/Follower 和 ISR 机制复制，不是每个业务分区都运行一套 Raft。**

```text
Controller quorum（例如 3 个投票节点）
    ↓ 通过 Raft 选出 active controller
active controller 协调元数据变更
    ↓ 元数据日志经多数派复制提交
Broker 获取并应用集群元数据
    ↓ 按分区 Leader / Follower 角色提供服务
Producer 和 Consumer 直接与相应 Broker 读写业务数据
```

KRaft 节点可以只承担 Broker 角色、只承担 Controller 角色，也可以同时承担两种角色。生产环境通常分离两种角色，以减少资源竞争和故障相互影响，代价是需要额外部署和管理 Controller 节点。

### Controller 多数派与数据副本是两种容错机制

3 个 Controller 投票节点通常可以容忍 1 个故障，5 个可以容忍 2 个，前提是剩余多数节点能够正常通信。失去多数派后，元数据变更和故障接管会受阻；已有分区是否还能继续读写，要看当前 Leader 和数据副本状态，不能简单等同于所有数据立刻不可读。

业务分区配置 3 个副本，也不代表一定能在任意 2 个 Broker 故障后继续写入；是否可用还取决于剩余 ISR、Leader 选举和 `min.insync.replicas` 等条件。Controller 的多数派与业务分区的 ISR 不能互换解释。

### 当前架构与历史版本边界

| 版本背景 | 阅读时怎样理解 |
|---|---|
| 《Kafka 权威指南》第二版 | Topic、分区、副本、生产者和消费者组等基础概念仍适用；集群协调部分需注意 ZooKeeper 背景 |
| Kafka 3.3 | KRaft 达到生产可用阶段 |
| Kafka 3.5 | ZooKeeper 模式被标记为弃用 |
| Kafka 4.0 起 | 移除 ZooKeeper 模式，使用 KRaft |

KRaft 版本背景可结合 [Kafka 4.0 升级说明](https://kafka.apache.org/40/getting-started/upgrade/)核对。讨论现代 Kafka 时，不应再说 Kafka 必须依赖 ZooKeeper。

## 容易混淆的说法

| 说法 | 更准确的理解 |
|---|---|
| Broker 就是分区 | Broker 是服务节点，一个节点保存多个分区副本 |
| 3 分区、3 副本就是 9 路组内消费并行 | 普通消费者组只有 3 个逻辑分区可分配，副本不增加分区数 |
| 同一个 Topic 的所有 Consumer 平分消息 | 只有同一消费者组内分担；不同组独立读取 |
| 订阅之后 Broker 会主动推送 | 普通 Consumer 主动拉取，订阅用于声明读取范围 |
| 消息被消费就会删除 | 消费进度与日志保留策略分开管理 |
| offset 是 Topic 的全局消息编号 | offset 只在对应分区内定位消息，也不保证可读记录之间连续 |
| 有副本就一定不会丢消息 | 还要看确认、ISR、选举和故障条件 |
| KRaft 的 Leader 就是业务分区的 Leader | active controller 管理元数据，分区 Leader 提供对应业务分区的数据读写 |

关于顺序写、Page Cache、批量和零拷贝，见 [Kafka 的核心概念和为什么快](kafka-概念和特性.md)。

**Kafka 用 Topic 分类消息，用分区扩展并行度，用副本应对节点故障；生产者向分区 Leader 写入，普通消费者组订阅后分配分区并主动拉取，各组独立记录进度，KRaft 则负责集群元数据的一致性与协调。**

## 消息传递语义与事务边界

| 语义 | 故障下的结果 | 常见做法 |
|---|---|---|
| 至多一次（At-most-once） | 可能漏处理 | 先推进进度再处理，接受失败消息被跳过 |
| 至少一次（At-least-once） | 可能重复处理 | 业务成功后提交，外部操作幂等 |
| 恰好一次（Exactly-once） | 需要明确事务范围 | Kafka 内读—处理—写将输出与输入位点纳入同一事务；外部系统需额外配合 |

幂等生产者减少协议重试造成的重复追加，不消除应用重新发送或数据库重复写。Kafka 事务可覆盖多分区输出和输入位点，下游通常配合已提交读（Read Committed），避免读取中止事务。它不是任意外部系统的通用分布式事务。

## 五类核心 API

生产者 API 写入事件，消费者 API 读取事件，管理 API 管理 Topic / 配置 / ACL，Kafka Connect 通过连接器持续导入导出数据，Kafka Streams 提供流处理应用库。Connect 是独立框架，Streams 是 Java 库；使用 Sarama 不等于具备它们的全部接口。

Kafka 4.2 起生产就绪的共享组允许多名消费者合作处理同一分区中的不同记录，其并行规则不同于传统消费者组。详见 [重平衡与共享组](kafka-重平衡与共享组.md)。
