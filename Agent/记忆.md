# Agent 记忆

## 1. 为什么 Agent 需要记忆

大语言模型本身通常不跨请求持有对话状态；每次调用可用的信息由当前输入和上下文窗口决定。把必要信息组织成记忆并在后续步骤中读写，才能让 Agent 延续多轮对话、跨会话个性化，并完成长流程任务。

记忆不是“把所有历史都塞回提示词”。上下文窗口有限，历史越长，输入成本和延迟通常越高，也会引入无关信息、干扰当前判断。因此系统要判断：

- 哪些信息值得保留，哪些可以丢弃或压缩；
- 什么时候从记忆中读取，读取哪些内容；
- 任务变化或信息过期时如何更新、纠正和删除；
- 如何在可用上下文预算内提供与当前目标相关的信息。

记忆可视为 Agent 外部的状态管理机制：模型负责理解和生成，记忆系统负责跨步骤保存、检索和维护信息。

## 2. 记忆类型与边界

| 类型 | 时间范围 | 主要内容 | 典型载体 | 主要用途 |
| --- | --- | --- | --- | --- |
| 短期记忆（Short-term memory） | 当前会话或当前任务 | 最近对话、尚未完成的步骤、临时上下文 | 对话消息列表、会话状态、检查点 | 保持当前交互连贯，支持任务继续执行 |
| 长期记忆（Long-term memory） | 跨会话、较长时间 | 用户偏好、稳定事实、历史经验、领域知识 | 数据库、文档库、向量索引等 | 个性化、跨会话回忆、知识复用 |
| 工作记忆（Working memory） | 当前推理/执行周期 | 当前目标、计划、约束、已完成事项、待办和中间结果 | 状态对象、Scratchpad、结构化任务记录 | 组织多步骤任务，避免遗忘当前进度 |

三者可以同时存在，但职责不同：短期记忆保存交互轨迹；长期记忆提供跨会话可复用的信息；工作记忆聚焦当前任务的可操作状态。工作记忆可能由短期消息、长期检索结果和 Agent 生成的状态共同构成，不必等同于某种特定数据库。

## 3. 短期记忆

### 3.1 对话历史与上下文窗口

最直接的短期记忆实现是把消息按顺序保存在会话中，并在下一次模型调用时重新提供。它实现简单，能保留原始措辞和交互细节，但历史增长会受上下文窗口限制。

控制历史时，常见策略有全量保留、滑动窗口和摘要。它们不是互斥方案：长会话通常先保留一份历史摘要，再拼接最近若干轮原文。

| 策略 | 适用对话轮数（经验值） | 适用情况 | 主要风险 |
| --- | --- | --- | --- |
| 全量历史 | 约 1–8 轮短对话 | 对话短；任务依赖前文原始措辞、细节或逐轮证据；总 token 明显低于预算 | 长输入成本高，历史增长后可能超出上下文窗口 |
| 滑动窗口 | 约 8–30 轮，或持续进行的普通会话 | 近期上下文最重要；较早细节不常被引用；希望保留原文而控制输入规模 | 窗口外的目标、约束或决定会被丢弃 |
| 摘要 | 通常超过约 20–30 轮，或较早信息仍持续影响任务时 | 长期任务、多阶段协作、早期决策和约束需要延续，但不必保留全部原话 | 压缩可能遗漏细节、改变语气或把推断误记为事实 |

轮数只是初始经验，不是固定切换线。短对话中一条代码、日志或长文就可能消耗大量 token；反过来，许多简短闲聊即使 token 不多，也可能让上下文充满低价值消息。应同时按轮数和 token 数控制滑动窗口：配置 `max_turns` 与 `max_tokens`，任一超限就从最旧处继续移除完整对话轮次，直到两个限制都满足。保留最近的完整用户/助手轮次，避免只留下回答或问题而丢失对应上下文；系统提示、工具定义等固定内容应单独计入总上下文预算，不应作为普通历史轮次裁剪。

摘要不必等到固定轮数才启动。当历史 token 达到可用上下文预算的一定比例、窗口裁剪将丢失关键约束，或任务跨越多个阶段时，可以提前生成/更新摘要。推荐组合为“旧历史摘要 + 最近若干轮原文”，并始终给最新对话留出预算。

### 3.2 全量历史、滑动窗口与摘要的选择

- **全量历史**：默认用于短对话。若消息中包含长代码、表格、日志或附件提取文本，即使只有几轮，也应尽早切换到窗口或摘要。
- **滑动窗口**：适用于轮次较多但主要依赖近期上下文的聊天。配置双重阈值：`max_turns` 防止大量短消息挤占注意力，`max_tokens` 防止少量超长消息撑爆上下文；任一超限都继续裁剪最旧轮次。
- **摘要**：适用于较长且有跨阶段连续性的任务。摘要提示应明确要求保留用户需求、已确认决策、偏好、硬性约束、关键事实及来源、已完成工作、未解决问题和下一步；区分事实与推断，不确定内容要标注。
- **混合策略**：长对话优先使用“摘要 + 滑动窗口”。摘要承接较早但仍有效的信息，窗口保留近期原文细节；若原话准确性很重要，保留原始记录或可回查引用，不要只依赖摘要。

示例起点可以设为全量最多约 8 轮；超过后启用窗口（例如最近 8–16 轮，同时限制 token）；当会话超过约 20–30 轮、窗口开始丢失仍有效的早期信息，或任务本身跨阶段时，加入滚动摘要。按模型上下文长度、系统提示和工具开销调小或调大阈值，并为模型输出预留空间。不同任务应根据事实完整性要求调整，不能把轮数当作唯一标准。

### 3.3 对话摘要

摘要将冗长历史压缩成对后续任务有用的状态，例如：用户目标、已经确认的事实、偏好、已完成步骤、未解决问题和约束。好的摘要不是逐轮复述，而是面向后续行动保留信息。

摘要可在达到长度阈值时更新，也可在任务边界、上下文接近上限时生成。更新时应把旧摘要与新消息一起考虑，避免只总结最近几句导致早期关键信息消失。必要时将“用户明确提供的事实”与“模型推断”分开记录，并注明不确定性。

### 3.4 检查点与可恢复执行

长流程 Agent 可以保存会话或图执行状态的检查点（Checkpoint），例如消息、当前节点、任务变量和工具执行结果。发生超时、中断或需要人工确认时，系统可从检查点恢复，而非从头开始。

检查点的重点是保存足以继续执行的状态，不只是保存一段自然语言总结。涉及外部副作用的工具调用还应记录执行状态，避免恢复时重复扣款、重复提交等操作。

## 4. 长期记忆

### 4.1 内容与写入策略

长期记忆适合保存跨会话仍可能有用的信息，例如稳定偏好、用户背景、长期目标、反复出现的事实，以及从任务中归纳出的经验。临时、敏感、未经确认或很快过期的信息不应无条件写入。

写入前可评估：

- **重要性**：未来是否可能影响回答或行动？
- **稳定性**：信息是否可能很快改变？
- **可信度**：来自用户明确陈述、工具验证，还是模型推断？
- **时效性**：是否需要记录时间、有效期或复核条件？
- **隐私性**：是否有必要保存，是否应脱敏或避免持久化？

记忆应支持更新和删除，而不是只追加。新旧信息冲突时，要依据来源、时间和可信度处理，并避免把旧结论继续当作事实。

### 4.2 检索与使用

长期记忆一般不应整库注入提示词，而是在需要时检索相关片段。典型流程是：根据当前问题生成查询，在索引或数据库中找候选记忆，按相关性、时间、重要性等因素排序，筛选后放入当前上下文，再由模型结合当前输入作答。

语义向量检索可找到措辞不同但意思相近的内容；关键词检索适合精确实体、编号或原文匹配。生产系统可以混合检索，并加上元数据过滤、重排序和结果数量限制。检索结果应尽量保留来源和时间，使 Agent 能判断可信度及新旧。

长期记忆与检索增强生成（RAG）有相似的检索机制，但目标不完全相同：RAG 常侧重外部语料知识；个体化记忆还要处理用户归属、隐私、偏好变化、记忆更新和删除。

### 4.3 向量记忆的设计决策

#### 检索元数据

向量记录除记忆文本和 embedding 外，建议附加可过滤、排序和治理的 metadata：

| 字段 | 用途 |
| --- | --- |
| `user_id` | 租户/用户范围过滤；多用户系统每次检索和写入都必须校验归属，不能只依赖 collection 名称隔离 |
| `importance` | 重要性评分；检索时可设阈值或参与排序，过滤低价值噪声 |
| `type` | 记忆类别，如 `preference`、`fact`、`event`、`task`；支持按任务限定检索类型 |
| `source` | 来源类型，如 `explicit`（用户明确陈述）或 `extracted`（从对话归纳），便于决定可信度和更新规则 |
| `confidence` | 提取/归纳置信度；低置信记忆可降低排序权重或等待确认 |
| `expires_at` | 可选有效期；过期事实、短期目标应到期后过滤、复核或删除 |

用户规模较小时可按用户分 collection，便于组织和运维；用户数增长时，为避免 collection 数量膨胀，可采用共享 collection 并按 `user_id` metadata 过滤。无论物理上如何分区，授权边界都应在查询层强制校验，不能把检索相似度当成访问控制。

#### 提取模型与可靠性

从对话提取记忆是结构化任务，可用较轻量模型控制成本。页面示例给出的配置可作为一种实现参考，而非固定要求：

| 决策 | 示例选择 | 原因/注意事项 |
| --- | --- | --- |
| 提取模型 | `gpt-4.1-mini` | 结构化抽取通常不需要最强推理；具体模型应按当前可用性、质量和成本评测 |
| 温度 | `0.0` | 降低抽取结果波动，便于稳定地产生相同 schema |
| JSON 输出 | 启用 `response_format: json_object` | 降低格式错误；仍需校验字段、类型和必填项，不能将模型输出直接视为可信数据 |
| 失败兜底 | 捕获提取错误并返回空列表 `[]` | 记忆提取属于增强能力，失败不应阻断主对话；记录错误指标，避免静默吞掉系统性故障 |

提取提示应约束允许的记忆类型和字段，明确只抽取未来可能有用的信息，并区分用户原话与推断。写入前再做去重、冲突检查、用户归属校验及敏感信息策略检查。

### 4.4 端到端读写链路

```text
收到用户消息
  -> 按 user_id 检索相关长期记忆（可按 type、importance 等 metadata 过滤）
  -> 组装系统提示：系统角色 + 相关长期记忆 + 历史摘要
  -> 发送系统提示、短期滑动窗口中的近期消息和当前用户消息
  -> 获取模型回复
  -> 将本轮消息加入短期窗口，并按 max_turns / max_tokens 维护窗口
  -> 异步提取本轮对话中的候选记忆（回复可按设定长度截断，例如 200 字符）
  -> 校验、去重并写入长期记忆库
```

异步写入可降低用户可感知的回复延迟，但应确保后台任务可观测、可重试，并避免重复写入。截断回复仅是控制提取输入长度的工程选项；若被截掉的部分可能含重要事实，应改用摘要或结构化字段，而不是盲目截断。

### 4.5 工业级扩展与治理

- **丰富元数据**：保存 `source`（如 `explicit` / `extracted`）、`confidence`、`expires_at` 等字段，让检索可以考虑来源、可信度和时效性。
- **记忆衰减**：长期未被检索或使用的记忆可逐步降低排序权重；可参考 Generative Agents 的时近性衰减思路，并结合重要性和相关性，避免仅因时间久就淘汰稳定事实。
- **多用户隔离**：多租户检索必须使用 `user_id` 过滤，并在读写路径做租户校验。collection 可作为存储组织方式，但不能替代访问控制。
- **审计日志**：记录回答使用了哪些记忆 ID、检索分数/过滤条件及时间，以便解释和排查某条记忆如何影响回答；日志本身也要遵循隐私和保留期限要求。

### 4.6 生命周期

可把长期记忆维护拆为四个环节：

1. **提取**：从对话或任务中识别候选信息。
2. **整合**：去重、规范化，并与已有记忆比较。
3. **检索**：按当前任务查询和筛选相关记忆。
4. **更新/淘汰**：修正过时内容、处理冲突，或删除低价值信息。

## 5. 工作记忆

工作记忆是 Agent 为当前任务维护的“正在工作的状态”，帮助模型知道要达成什么、已经做了什么、接下来做什么，以及哪些规则不能违反。它可以用结构化字段或 Scratchpad（草稿区）表示。

一个实用的任务状态可以包含：

```text
目标：用户希望完成的结果
约束：格式、范围、资源和禁止事项
已知事实：已确认的输入与证据
计划：当前步骤及顺序
进度：已完成、进行中、待处理
中间产物：计算结果、工具返回值、草稿
风险/不确定项：冲突、缺失信息、待确认假设
下一步：紧接着要执行的动作
```

### 5.1 结构化状态优于纯长文本

纯自然语言 Scratchpad 灵活，但容易冗长、含糊或在多次更新后出现自相矛盾。结构化状态更便于程序读取、校验和恢复。实践中可以用结构化字段记录事实和进度，把需要解释的推理摘要作为补充，而不是把所有内部推理都长期保存。

### 5.2 状态更新原则

- 每完成一个有意义的步骤就更新进度和下一步。
- 区分事实、假设、计划和工具结果，不把计划写成已完成事实。
- 新证据到来时修正旧状态，并记录必要的来源。
- 控制粒度：保存继续任务所需内容，避免无关的逐步流水账。
- 恢复执行前检查状态是否仍然有效，尤其是外部资源和时效性数据。

## 6. 组合使用的实践模式

一次 Agent 请求可以按以下顺序处理：

1. 读取当前会话的短期上下文和任务状态。
2. 判断是否需要长期记忆；只检索与当前目标相关的内容。
3. 把目标、约束、证据和检索结果整理进工作记忆。
4. 执行任务，并在工具调用或关键阶段后更新工作状态。
5. 必要时压缩短期历史或保存检查点，保证任务可恢复。
6. 任务结束后，选择性提取值得跨会话保留的长期记忆。

核心原则是**按需读取、选择性写入、持续校验、可控压缩**。记忆的效果应以任务是否更连贯、更准确、更易恢复来评估，而不是以保存了多少文本来衡量。

## 7. 常见问题

- **把所有历史都塞进上下文**：成本高且噪声多；应摘要、筛选或检索。
- **把模型推断当成用户事实**：可能形成错误画像；应标注来源和置信度。
- **只写不更新**：旧偏好或过期信息会持续污染回答；需要冲突处理与删除机制。
- **只用向量相似度检索**：精确实体、时间和权限条件可能被忽略；可结合关键词、元数据过滤和重排序。
- **工作状态只写“正在处理”**：无法恢复；应记录已完成步骤、结果和明确的下一步。
- **摘要丢失出处**：难以核验；重要结论应保留来源、时间或原始记录引用。
