# RAG 检索评估

## 1. 评估目标

RAG 检索器的核心问题不是“返回了多少文档”，而是：**是否找到了与问题相关的文档，并且把最相关的文档排在前面**。

除了质量，还要关注系统性能：

| 维度 | 关注问题 | 常用指标 |
| --- | --- | --- |
| 搜索质量 | 是否找到相关文档，是否遗漏或混入无关文档 | Precision、Recall、MRR、mAP、nDCG |
| 排名质量 | 相关文档是否位于前几名 | Precision@K、Recall@K、AP@K、MAP@K |
| 延迟 | 用户发起查询到结果返回耗时多久 | P50、P95、P99 延迟 |
| 吞吐 | 单位时间能处理多少查询 | QPS、每秒查询数 |

质量通常比吞吐和延迟更重要：检索很快，但返回的文档不相关，RAG 生成结果仍然会错误。

## 2. 评估所需的三类数据

一次检索评估至少需要以下三项：

1. **提示词（Prompt/Query）**：正在测试的用户问题。同一个检索器可能对不同提示词表现不同。
2. **排序结果（Ranked Results）**：检索器返回的文档 ID 列表及其顺序，例如 `[D3, D8, D1, D5]`。
3. **真实值（Ground Truth）**：人工标注或业务规则确认的相关文档集合，例如 `{D1, D3, D7}`。

没有真实值，就无法判断“返回的文档是否正确”，也无法可靠计算精确率、召回率等离线指标。

建议将评估集保存为结构化数据：

```json
{
  "query_id": "q-001",
  "query": "如何配置 Kafka 的幂等生产者？",
  "relevant_doc_ids": ["doc-12", "doc-19"],
  "retrieved_doc_ids": ["doc-19", "doc-03", "doc-12", "doc-44"]
}
```

真实值可以是二值标注（相关/不相关），也可以是分级标注（0=不相关，1=部分相关，2=高度相关）。评估集应覆盖常见问题、长尾问题、同义表达、错误码和版本号等场景。

## 3. 精确率与召回率

设：

- `R`：真实相关文档集合；
- `A`：检索器返回的文档集合；
- `|A ∩ R|`：返回结果中真正相关的文档数量。

### 3.1 精确率（Precision）

精确率衡量返回结果的可信度，惩罚返回无关文档：

```text
Precision = |A ∩ R| / |A|
           = 返回的相关文档数 / 返回文档总数
```

例如，返回 12 篇文档，其中 8 篇相关：

```text
Precision = 8 / 12 ≈ 66.7%
```

精确率高，表示“返回的内容大多有用”；但只返回 1 篇且恰好相关，也可能得到 100% 精确率，因此它不能单独说明是否找全。

### 3.2 召回率（Recall）

召回率衡量检索的全面性，惩罚遗漏相关文档：

```text
Recall = |A ∩ R| / |R|
        = 返回的相关文档数 / 全部相关文档数
```

如果知识库中共有 10 篇真实相关文档，检索返回其中 8 篇：

```text
Recall = 8 / 10 = 80%
```

### 3.3 二者的权衡

扩大返回数量通常会提高召回率，但可能混入更多无关文档，导致精确率下降；缩小返回数量通常相反。理想结果是把所有相关文档排在最前面，并只返回这些文档，但实际系统通常需要在二者之间取舍。

## 4. Top-K 指标

RAG 往往只把前 `K` 篇文档交给重排器或 LLM，因此应评估前 `K` 个结果，而不是只看完整结果集。

### 4.1 Precision@K

```text
Precision@K = 前 K 个结果中的相关文档数 / K
```

例如前 10 篇中有 6 篇相关：

```text
Precision@10 = 6 / 10 = 60%
```

### 4.2 Recall@K

```text
Recall@K = 前 K 个结果中的相关文档数 / 全部相关文档数
```

若真实相关文档有 8 篇，前 10 名找到了其中 6 篇：

```text
Recall@10 = 6 / 8 = 75%
```

### 4.3 严格与宽松的 Top-K

常见的观察范围包括：

| 范围 | 典型用途 | 特点 |
| --- | --- | --- |
| Top-1、Top-5 | 生成上下文很短、首条结果必须准确的场景 | 严格，强约束前排结果 |
| Top-5～Top-15 | 通用 RAG 候选召回和重排 | 更宽松，关注候选覆盖率 |

`K` 不是越大越好：过大的上下文会增加延迟、成本和噪声。应根据下游模型上下文窗口和业务容错度选择。

## 5. 平均精确度（AP）

Precision@K 只看一个固定位置；平均精确度（Average Precision，AP）还会奖励相关文档出现在更前面。

对单个查询，设前 `K` 个结果的相关性为 `rel(i)`：相关为 1，不相关为 0。则：

```text
P@i = 前 i 个结果中的相关文档数 / i

AP@K = Σ(i=1..K) [P@i × rel(i)] / min(相关文档总数, K)
```

只在第 `i` 个结果相关时，把该位置的 `P@i` 加入总和；不相关位置不贡献分数。

### 示例

排序结果前 6 名如下，真实相关文档为 3 篇：

| 排名 `i` | 结果 | 是否相关 | `P@i` |
| ---: | --- | ---: | ---: |
| 1 | D1 | 1 | 1/1 = 1.00 |
| 2 | D2 | 0 | 1/2 = 0.50 |
| 3 | D3 | 0 | 1/3 ≈ 0.33 |
| 4 | D4 | 1 | 2/4 = 0.50 |
| 5 | D5 | 1 | 3/5 = 0.60 |
| 6 | D6 | 0 | 3/6 = 0.50 |

相关结果位于第 1、4、5 名，因此：

```text
AP@6 = (1.00 + 0.50 + 0.60) / 3
     = 2.10 / 3
     = 0.70
```

如果相关文档更早出现，AP 会更高；即使相关文档数量相同，排名靠后的结果也会降低 AP。

## 6. mAP@K

平均精确度均值（Mean Average Precision，mAP）是多个查询 AP 的平均值：

```text
mAP@K = (AP@K(query₁) + AP@K(query₂) + ... + AP@K(queryₙ)) / n
```

例如 3 个查询的 `AP@10` 分别为 `0.70`、`0.50`、`1.00`：

```text
mAP@10 = (0.70 + 0.50 + 1.00) / 3
        = 0.7333 ≈ 73.3%
```

`mAP@K` 同时关注“相关文档有没有被召回”和“相关文档是否排名靠前”，适合比较不同 Embedding 模型、分块策略、混合检索权重或重排器。计算时应明确：`K` 的取值、相关性标注规则，以及没有返回任何相关文档时 AP 如何记分（通常为 0）。

## 7. 互惠排名与平均互惠排名

### 7.1 互惠排名（Reciprocal Rank）

互惠排名只关注**第一个相关文档**在返回列表中的位置：

```text
RR = 1 / rank
```

其中 `rank` 从 1 开始。如果第一个相关文档位于第 1、2、4 名，互惠排名分别为 `1.00`、`0.50`、`0.25`。相关文档出现得越晚，分数下降越快；如果整个列表没有相关文档，通常记为 `RR = 0`。

### 7.2 平均互惠排名（MRR）

平均互惠排名（Mean Reciprocal Rank，MRR）是多个查询互惠排名的平均值：

```text
MRR = (RR₁ + RR₂ + ... + RRₙ) / n
    = (1/rank₁ + 1/rank₂ + ... + 1/rankₙ) / n
```

例如 4 个查询的第一个相关文档分别位于第 1、3、6、2 名：

| 查询 | 第一个相关文档排名 | RR |
| --- | ---: | ---: |
| Search 1 | 1 | 1/1 = 1.00 |
| Search 2 | 3 | 1/3 ≈ 0.33 |
| Search 3 | 6 | 1/6 ≈ 0.17 |
| Search 4 | 2 | 1/2 = 0.50 |

```text
MRR = (1.00 + 0.33 + 0.17 + 0.50) / 4
    = 2.00 / 4
    = 0.50
```

MRR 反映检索器需要多快才能找到一个可用的相关文档，并强调把至少一个相关文档排在高位。它适合问答、导航和“用户通常只需要一个正确答案”的场景。

MRR 的限制是只看第一个相关文档：第 1 名之后还有多少相关文档、是否找全，不会影响该查询的 RR。因此需要覆盖多个相关文档时，应同时观察 Recall@K、AP 或 mAP。

### 7.3 指标选择

| 目标 | 更适合的指标 |
| --- | --- |
| 找到尽可能多的相关文档 | Recall、Recall@K |
| 前 K 个结果尽量少混入无关文档 | Precision@K |
| 多个相关文档都要靠前 | AP@K、mAP@K |
| 只要尽快找到一个可用文档 | RR、MRR |

所有这些指标都依赖 Ground Truth；没有标注的相关文档集合，就无法判断结果是否正确。

## 8. 其他常用排名指标

| 指标 | 公式或含义 | 适用场景 |
| --- | --- | --- |
| MRR | `1 / 第一个相关结果的排名`，再对多个查询取平均 | 用户通常只需要一个正确答案 |
| nDCG@K | 按位置折损的累计增益，支持 0/1/2 等分级相关性 | 相关程度有等级，且排序位置很重要 |
| Hit Rate@K | 前 K 名是否至少命中一个相关文档 | 只关心“有没有找到一个可用答案” |

这些指标不能互相替代：MRR 偏向首个正确结果，Recall@K 偏向覆盖全部相关文档，mAP@K 同时评价多个相关文档的排名。

## 9. 吞吐与延迟评估

质量指标应与性能指标一起记录：

```text
吞吐（QPS） = 完成的查询数 / 测试时间（秒）
延迟 = 请求结束时间 - 请求开始时间
```

不要只报告平均延迟。平均值可能掩盖少数极慢请求，通常至少报告 P50、P95 和 P99：

- **P50**：一半请求不超过该耗时，代表典型体验；
- **P95**：95% 请求不超过该耗时，代表大多数用户体验；
- **P99**：99% 请求不超过该耗时，用于发现长尾问题。

测试时固定数据集、并发数、`top_k`、过滤条件、Embedding 模型和硬件环境，否则不同版本的指标不可直接比较。应分别记录向量召回、关键词召回、重排、网络和总耗时，定位瓶颈。

## 10. 推荐评估流程

```text
定义问题与业务目标
  → 建立查询集
  → 标注每个查询的真实相关文档
  → 运行检索器并保存排序结果
  → 计算 Precision@K、Recall@K、AP@K、mAP@K
  → 同时记录 P50/P95/P99 延迟和 QPS
  → 对比参数、模型或检索策略
  → 在独立测试集上复验
```

最小可行评估应至少包含：

1. 明确的查询集和 Ground Truth；
2. 固定的 `K`（例如 `K=5`、`K=10`）；
3. `Precision@K` 与 `Recall@K`；
4. 能反映排名先后的 `mAP@K` 或 MRR；
5. 延迟分位数和吞吐；
6. 按问题类型拆分结果，而不只看一个总体平均数。

## 11. 常见误区

- **没有 Ground Truth 就宣称检索质量高**：只能说明系统返回了结果，不能说明结果正确。
- **只看精确率**：返回很少结果时精确率可能很高，但召回率很低。
- **只看召回率**：返回大量文档可以提高召回率，却会引入噪声和成本。
- **只看完整结果集**：RAG 通常只使用 Top-K，必须评估前排结果。
- **把 BM25 的“25”当成 Top-25**：BM25 是算法名称，不代表返回 25 篇文档。
- **混淆 AP 与 mAP**：AP 针对一个查询，mAP 是多个查询 AP 的平均值。
- **只报告平均延迟**：长尾请求可能严重影响实际用户体验，应报告 P95/P99。

## 12. 总结：检索技术与评估指标

### 12.1 三类检索技术

| 技术 | 排序或过滤依据 | 典型优势 |
| --- | --- | --- |
| 关键词搜索（Keyword Search） | 关键词频率和精确词面匹配 | 适合错误码、版本号、专有名词，结果容易解释 |
| 语义搜索（Semantic Search） | 文本 Embedding 的语义相似度 | 能识别同义表达，表达更灵活 |
| 元数据过滤（Metadata Filtering） | 日期、作者、权限、地区等固定条件 | 快速排除不符合范围或无权访问的文档 |
| 混合检索（Hybrid Search） | 组合关键词、语义和元数据过滤 | 同时覆盖精确匹配、语义匹配和范围控制 |

混合检索不是第四种独立的相关性信号，而是将三类能力组合起来：元数据过滤先确定候选范围，关键词和语义检索负责召回与排序，随后通过加权分数或 RRF 融合结果。

### 12.2 用指标验证参数调整

混合检索中的权重、`top_k`、BM25 参数、Embedding 模型和重排器都应通过同一评估集比较。每次调整至少记录：

| 目标 | 观察指标 |
| --- | --- |
| 是否找全相关文档 | Recall、Recall@K |
| 是否减少无关文档 | Precision、Precision@K |
| 是否把相关文档提前 | mAP@K、MRR |
| 是否满足线上性能目标 | P50/P95/P99 延迟、QPS |

只有在固定查询集、Ground Truth、`K` 和测试环境下比较，才能判断参数调整是否真正改善检索器。指标提升应同时检查延迟、吞吐和权限正确性，避免只优化离线分数而损害实际体验。
