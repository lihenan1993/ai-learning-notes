# RAG 成本、延迟与响应质量

RAG 生产系统不能只追求答案质量。更实用的目标是：在满足业务质量底线的前提下，控制单次请求成本和用户等待时间，并能通过观测数据持续调整组件。

## 1. 三个核心目标

| 目标 | 要回答的问题 | 常用指标 |
| --- | --- | --- |
| 成本 | 一次请求花了多少资源和费用？ | 输入/输出 Token、模型调用次数、Embedding 次数、向量库资源成本、单请求成本 |
| 延迟 | 用户等了多久，瓶颈在哪里？ | 端到端延迟、首 Token 延迟、P50/P95/P99、各阶段耗时 |
| 质量 | 回答是否正确、相关、完整且可引用？ | 检索 Recall@K、答案正确性、忠实性、引用准确率、用户反馈 |

三者通常存在权衡：更大的模型和更长的上下文可能提高质量，但也会增加 Token 成本和延迟；过度压缩模型或上下文则可能造成质量下降。优化目标应按业务场景设定，而不是追求单一指标最大化。

## 2. 延迟为什么重要

延迟容忍度取决于场景：

| 场景 | 速度优先级 | 质量优先级 | 典型取舍 |
| --- | --- | --- | --- |
| 电商推荐、客服对话 | 很高 | 中等 | 可牺牲部分答案质量，换取快速响应 |
| 医疗辅助、风险判断 | 较低 | 很高 | 可以忍受更高延迟，但必须提高正确性、可追溯性和安全性 |

一次 RAG 请求可以拆成：

```text
查询处理 → 检索 → 重排 → 上下文拼接 → LLM 生成
```

通常主要延迟来自 Transformer/LLM 调用，尤其是模型首 Token 和生成阶段；查询处理、检索和数据库操作也必须单独计时，避免把局部瓶颈误认为模型瓶颈。

## 3. 降低 LLM 成本和延迟

### 3.1 使用更小的模型

- 使用较小的核心模型，或减少代理系统中各组件调用的模型规模；
- 使用量化模型，在可接受的质量损失下减少显存占用和推理成本；
- 对单一任务使用小模型微调，避免让通用大模型处理固定格式任务；
- 使用较小的路由器模型决定问题应进入哪条处理路径。

### 3.2 缩短提示词和输出

- 减少检索文档数量，合理设置 `top_k`；
- 通过系统提示词约束回答长度，设置合理的输出 Token 上限；
- 删除重复上下文、无关字段和过大的历史对话；
- 在质量允许时，使用更短的文档分块和更紧凑的上下文模板。

### 3.3 缓存

- 缓存稳定的提示词、检索结果或最终回答；
- 对个性化场景，可先读取缓存内容，再交给较小的 LLM 按用户上下文改写；
- 缓存键应包含问题规范化结果、知识库版本、提示词版本、租户或权限范围，避免返回过期或越权内容；
- 记录命中率、节省的 Token、缓存引入的质量回归和失效原因。

缓存不是无条件启用：知识更新频繁、权限差异大或回答时效性要求高的场景，需要缩短 TTL 或只缓存中间结果。

## 4. 组件增量价值评估

每个组件都应同时记录自己的耗时、成本和带来的质量变化。可将一次请求表示为：

```text
组件增量价值 = 质量提升 / (额外延迟 + 额外成本)
```

公式用于比较，不必把质量、毫秒和货币强行合并成一个绝对分数。评估时至少做有/无组件的对照实验：

| 组件 | 记录内容 | 可能的剔除条件 |
| --- | --- | --- |
| 查询改写 | 耗时、改写后检索指标、最终答案质量 | 质量提升很小且延迟明显增加 |
| 路由器 LLM | 路由耗时、选路准确率、各模型成本 | 路由错误或节省成本不足以抵消调用成本 |
| 重排器 | 重排耗时、Recall@K、答案引用准确率 | 质量提升很小且成为长尾瓶颈 |
| 额外检索源 | 数据源耗时、覆盖率、答案正确性 | 很少贡献有效证据或引入大量噪声 |

如果某组件没有显著提高质量，却带来较大的延迟或费用，应直接剔除、降级为按需调用，或只在高风险问题上启用。

## 5. 向量数据库的成本优化

### 5.1 量化

向量量化使用更低精度的数据表示，减少存储、内存和距离计算成本。应在固定评估集上比较压缩前后的 Recall@K、MRR、P95 延迟和资源占用，确认质量损失在业务可接受范围内。

### 5.2 分层存储

| 存储层 | 特点 | 适合内容 |
| --- | --- | --- |
| RAM | 最快，成本最高 | 热门租户、热查询和高频索引 |
| SSD/磁盘 | 较快，成本较低 | 一般访问频率的向量和索引 |
| 云对象存储 | 最慢，成本最低 | 原始文档、冷数据和归档内容 |

常见做法是把 HNSW 等热索引放在 RAM，把较少访问的向量移到 SSD/磁盘，把文档正文放在对象存储。查询命中冷数据时按需加载，避免让全部数据长期占用昂贵内存。

### 5.3 多租户和按需加载

- 按租户拆分文档和索引，避免每次查询扫描无关租户数据；
- 为租户维护独立或逻辑隔离的索引，并按访问热度动态放入 RAM 或慢速存储；
- 只有在租户有请求时才加载其索引；
- 对不同地区的租户，可结合业务活跃时间安排预热和迁移，减少全天候占用高速存储。

这些策略需要同时验证租户隔离、首次加载延迟、缓存命中率和索引更新时延。

## 6. 观测管道设计

一次请求至少应使用一个 `trace_id`，并为查询处理、检索、重排、上下文拼接和 LLM 调用分别记录 `span`。建议记录：

1. 各阶段开始/结束时间、首 Token 延迟和总耗时；
2. 模型、提示词、Embedding、索引和路由版本；
3. 输入/输出 Token、调用次数、缓存命中、估算费用；
4. `top_k`、返回文档 ID、分数、重排结果和引用来源；
5. 自动质量评分、人工抽检、点赞/点踩、追问率和错误信息；
6. 降级、超时、重试和剔除组件的原因。

敏感提示词和文档正文应按策略脱敏、采样和分级保留。日志要能关联基础设施指标，但不应为了观测而长期保存不必要的敏感内容。

## 7. 质量评估与决策闭环

质量评估至少分为三层：

| 层级 | 示例 | 作用 |
| --- | --- | --- |
| 检索质量 | Precision@K、Recall@K、MRR、nDCG@K | 判断证据是否找对、排对 |
| 生成质量 | 正确性、忠实性、完整性、引用准确率 | 判断回答是否基于证据且满足任务 |
| 线上反馈 | 点赞/点踩、改写率、追问率、解决率 | 发现离线评估遗漏的真实问题 |

推荐采用以下流程：

```text
固定评估集与线上样本
  → 记录成本、延迟和质量基线
  → 逐个启用或关闭组件做对照
  → 比较质量增量、P95/P99 延迟和单请求成本
  → 保留满足质量底线且性价比高的组件
  → 灰度发布并持续监控回归
```

不要只看总体平均值，应按业务场景、问题类型、模型版本、知识库版本和租户拆分。最终决策可以用约束表达：

```text
在质量 ≥ 业务底线、P95 延迟 ≤ 场景目标的条件下，最小化单请求成本
```

## 8. 最小落地清单

1. 为每次请求记录端到端和各阶段 P50/P95/P99 延迟；
2. 记录输入/输出 Token、模型调用次数、缓存命中率和单请求成本；
3. 固定一套带 Ground Truth 的评估集，计算 Recall@K、MRR 或答案正确性；
4. 建立组件开关，能做有/无组件的对照实验；
5. 将模型、提示词、索引和评估集版本写入 Trace；
6. 设定质量底线、延迟目标和成本预算，触发降级或回滚；
7. 对向量索引验证量化、分片、分层存储和按需加载的收益与质量损失。

优化不是把每个组件都做得更复杂，而是用观测数据确认它是否值得存在：质量提升不足以覆盖延迟和成本时，就删除或限制它的使用范围。
