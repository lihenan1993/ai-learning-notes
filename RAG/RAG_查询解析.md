# RAG 查询解析

> 本篇负责概念全景（查询重写、NER、HyDE 的定义、提示模板、选择顺序）。
> 改写技术的分类修正、2025–2026 进展、本机实测数据与面试答法见 `RAG_Query改写.md`。

## 1. 为什么需要查询解析

用户提示词可能口语化、含糊、冗余，甚至与知识库中的术语不一致。直接把原始提示交给检索器，可能导致查询向量偏离真正意图，降低相关文档的召回率和排名质量。

查询解析（Query Parsing）是在检索前理解、改写或结构化用户查询的过程。目标不是改变用户意图，而是生成更适合检索的查询表示。

典型流程如下：

```text
用户原始提示
    ↓
查询解析器（LLM、规则或 NER 模型）
    ↓
优化后的查询 / 实体 / 假设性文档
    ↓
关键词检索、语义检索或混合检索
    ↓
候选文档
```

查询解析会增加额外延迟和成本，因此应通过检索评估验证收益，而不是默认叠加所有高级技术。

## 2. 查询重写

### 2.1 定义与流程

查询重写（Query Rewriting）使用 LLM 或规则，在查询提交给检索器前把原始提示改写为更清晰、更适合搜索的表达。

```text
原始提示词 → 查询重写器 → 优化查询 → 检索器
```

查询重写器可以完成以下工作：

- 澄清含糊或指代不明的表达；
- 使用知识库中更可能出现的领域术语；
- 增加有助于匹配的同义词、缩写或完整名称；
- 删除与检索目标无关的背景信息；
- 保留时间、地点、版本、产品等关键限制条件。

### 2.2 示例

原始查询：

> 这个东西老是连不上，之前改过配置，怎么处理？

优化查询：

> 排查服务无法连接的问题，重点检查最近修改的网络、认证和连接配置，并查找包含连接失败处理步骤的故障文档。

如果原始查询包含具体信息，重写器应保留这些信息，例如服务名称、错误码、版本号和发生时间。

### 2.3 推荐提示模板

```text
你是检索查询优化器。请将用户问题改写成适合知识库搜索的查询。

要求：
1. 保留用户的真实意图、时间范围、产品、版本号、错误码和其他约束；
2. 澄清含糊表达，补充必要的领域术语和常见同义词；
3. 删除与检索无关的礼貌用语和背景叙述；
4. 不要回答问题，不要编造用户未提供的事实；
5. 只输出一条简洁的优化查询。

用户问题：{user_query}
```

### 2.4 优势与风险

| 优势 | 风险与控制方式 |
| --- | --- |
| 实现简单，容易接入现有检索流程 | LLM 可能误解原意；要求保留约束并记录原始查询 |
| 能改善口语、同义词和长背景导致的检索问题 | 重写结果可能丢失错误码、版本号等精确词面；保留关键实体 |
| 额外延迟和成本相对可控 | 对简单查询不一定有收益，可按查询类型选择性启用 |

## 3. 命名实体识别

### 3.1 定义

命名实体识别（Named Entity Recognition，NER）从查询中识别并分类具有特定含义的片段，例如地点、日期、人物、组织、产品、书名、版本号和错误码。

示例：

> 我去年夏天在纽约读了《了不起的盖茨比》，有没有类似的 20 世纪 20 年代小说？

| 实体文本 | 类型 |
| --- | --- |
| 《了不起的盖茨比》 | 作品 / 书籍 |
| F. Scott Fitzgerald | 人物 |
| 纽约 | 地点 |
| 去年夏天 | 日期或时间 |
| 20 世纪 20 年代 | 日期或时间范围 |

实体识别后，可以把实体用于向量检索中的查询补充，也可以映射到元数据字段进行过滤。

### 3.2 在 RAG 中的用法

```text
用户查询
  ├─ 实体识别 → 实体类型与标准化值 → 元数据过滤
  └─ 原始/重写查询 → Embedding → 语义检索
```

例如，识别出 `产品 = Kafka`、`版本 = 4.x`、`日期范围 = 2026 年` 后，可以优先检索 Kafka 4.x 的文档，并过滤不符合版本或时间范围的资料。

权限、租户和订阅等级等安全条件必须来自可信的用户身份与授权策略，不能仅根据用户在查询中自称的实体或属性放行。

### 3.3 优势与代价

| 优势 | 代价或风险 |
| --- | --- |
| 支持更精确的元数据过滤 | 需要额外模型、规则或标注维护 |
| 有助于标准化产品名、版本号和别名 | 实体边界或类型判断可能出错 |
| 对结构化领域和精确条件尤其有用 | 会增加解析延迟；实体类型不稳定时可能过滤过严 |

NER 适合实体丰富、元数据完善且过滤收益明确的系统。若知识库没有对应的元数据字段，单独做 NER 的收益可能有限。

## 4. 假设性文档嵌入（HyDE）

### 4.1 核心思想

假设性文档嵌入（Hypothetical Document Embeddings，HyDE）先根据用户问题生成一段假设性的理想答案或文档，再对这段假设文档做 Embedding，并用它检索真实知识库。

普通语义检索是：

```text
用户查询 → 查询向量 → 匹配真实文档向量
```

HyDE 是：

```text
用户查询 → LLM 生成假设性文档 → 假设文档向量 → 匹配真实文档向量
```

它把“问题的表达方式”转换为“可能出现在答案文档中的表达方式”，因此有时能提高语义匹配效果。检索器匹配的仍是真实文档；假设性文档只是查询表示，不应直接作为事实依据。

### 4.2 示例

用户问题：

> Kafka 生产者怎么避免消息丢失？

LLM 生成的假设性文档可能包含：

> Kafka 生产者可以通过等待 broker 确认、设置 `acks=all`、启用幂等生产者，并合理配置重试来降低消息丢失风险。还需要结合副本同步和故障处理策略验证可靠性。

系统对这段假设性文档进行 Embedding，再检索知识库中真实的生产者可靠性配置文档。

### 4.3 优势与代价

| 优势 | 代价或风险 |
| --- | --- |
| 查询向量更接近答案文档的语言分布 | 需要额外调用 LLM，增加延迟和成本 |
| 对短查询、抽象问题或词面差异大的问题可能有效 | 假设文档可能包含幻觉，导致检索方向偏移 |
| 可与原始查询向量结合，保留原始词面 | 对已有高质量查询的收益可能不明显 |

HyDE 生成内容只用于检索表示，不能绕过真实文档验证，也不能直接作为最终答案。

## 5. 三种方法对比

| 方法 | 主要输出 | 最适合解决的问题 | 主要代价 |
| --- | --- | --- | --- |
| 查询重写 | 更适合搜索的文本查询 | 口语、冗余、歧义、术语不一致 | 一次额外推理调用或规则处理 |
| 命名实体识别 | 实体及其类型、标准化值 | 产品、版本、日期、地点等条件过滤 | 模型和字段维护，可能误识别或过度过滤 |
| HyDE | 假设性文档的向量 | 查询与文档措辞差异大、问题较抽象 | 额外生成和 Embedding 成本，可能引入幻觉 |

三种方法可以组合，但组合越多，延迟、成本和故障点越多。应分别测量每一步对 Recall@K、Precision@K、MRR、mAP@K 和延迟的影响。

## 6. 实践选择顺序

建议按以下顺序逐步引入：

1. **先建立基线**：记录原始查询的检索质量、延迟和成本。
2. **优先尝试查询重写**：实现简单，通常能处理最多的表达问题。
3. **需要结构化过滤时加入 NER**：只有在实体能够映射到可靠元数据或检索字段时才启用。
4. **词面差异明显且基线不足时测试 HyDE**：重点观察召回提升是否值得额外延迟和费用。
5. **按查询类型路由**：简单、精确的错误码查询可以跳过重写；抽象问题再启用更复杂的解析。

一般情况下，查询重写已经能覆盖大多数查询解析需求。NER 和 HyDE 属于高级技巧，应以离线评估和线上指标决定是否采用。

## 7. 最小实现伪代码

```python
def parse_query(user_query, metadata_filters=None):
    rewritten = rewrite_query(user_query)
    entities = extract_entities(rewritten) if metadata_filters else {}
    return rewritten, entities


def retrieve(user_query, use_hyde=False):
    rewritten, entities = parse_query(user_query, metadata_filters=True)
    query_vector = embed(rewritten)
    if use_hyde:
        hypothetical_doc = generate_hypothetical_document(rewritten)
        query_vector = embed(hypothetical_doc)
    return hybrid_search(rewritten, query_vector, entities)
```

实际系统应保存原始查询和解析结果，便于回溯重写错误、比较实验组，并在权限过滤后再进行相关性排序。

## 8. 评估清单

- 查询重写后 `Recall@K` 是否提高；
- 前排结果的 `Precision@K`、MRR 或 mAP@K 是否改善；
- 是否丢失错误码、版本号、日期等硬约束；
- NER 的实体识别准确率和过滤后的漏召回率；
- HyDE 带来的召回提升是否覆盖额外 LLM、Embedding 成本；
- P50、P95、P99 延迟是否仍满足目标；
- 失败时是否保留原始查询作为回退路径。
