# RAG 生产落地挑战

RAG（Retrieval-Augmented Generation，检索增强生成）从演示走向生产后，难点不只在于“能否检索到内容”，还在于系统能否在真实流量、复杂数据和不确定请求下持续提供稳定、合规且可解释的结果。常见挑战可以归纳为：性能扩展、提示不可预测、数据质量，以及安全与隐私。

## 1. 性能扩展（Scaling Performance）

随着用户和请求量增加，RAG 链路中的检索、过滤、重排、上下文拼接和 LLM 调用都会承受更高压力。

### 1.1 主要影响

- **流量增加**：请求更多，检索服务和模型服务的延迟、排队时间上升。
- **请求增加**：向量查询、关键词查询、重排和上下文处理带来更高的内存与计算成本。
- **性能保持困难**：系统扩容后仍要维持可接受的响应时间、吞吐量和回答质量。

### 1.2 生产应对

| 方向 | 实践要点 |
| --- | --- |
| 延迟拆解 | 分别记录查询改写、向量召回、关键词召回、过滤、重排、LLM 首 token 和总耗时 |
| 容量规划 | 用 P50、P95、P99 延迟和 QPS 评估并发、峰值流量与容量余量 |
| 检索优化 | 控制 `top_k`，先过滤再检索，避免把大量无关片段交给重排器和 LLM |
| 缓存与复用 | 对稳定的查询改写、Embedding 或热点结果使用已有缓存能力，并设置失效策略 |
| 降级策略 | 在重排或部分依赖不可用时，返回较小候选集、使用关键词检索或明确提示暂不可用 |

扩容不能只增加机器数量。过大的 `top_k`、重复上下文和过长提示词也会直接增加延迟与模型成本，因此性能指标必须和检索质量一起观察。

## 2. 提示词和用户请求的不可预测性

即使经过严格测试，也不可能枚举 RAG 系统将收到的所有请求。用户可能提出超出知识库范围、表达含糊、跨主题、恶意构造或完全不相关的问题。

### 2.1 典型情况

- 问题使用同义词、口语、错别字或多轮对话中的省略表达；
- 请求需要多个文档、多个步骤或跨数据源组合答案；
- 问题超出知识库覆盖范围，例如“我应该吃多少石头？”；
- 用户试图通过提示词注入，要求模型忽略系统规则或泄露受限内容；
- 同一个问题因时间、权限、用户角色不同而需要不同答案。

### 2.2 生产应对

1. **查询理解**：对问题进行分类、改写、补全上下文，并识别语言、时间范围和实体。
2. **范围判断**：检索前判断问题是否属于系统支持范围；没有可靠证据时允许拒答。
3. **多路检索**：结合关键词、语义检索和元数据过滤，覆盖精确术语与自然语言表达。
4. **输入防护**：限制提示词长度和请求频率，识别提示注入、越权请求及异常内容。
5. **持续评估**：按问题类型、用户群体和长尾场景拆分评估集，监控线上新问题并回流测试。

系统的目标不是预测每一个问题，而是在无法回答时稳定地识别边界、给出清晰反馈，并避免编造答案。

## 3. 混乱的真实世界数据（Messy Real-World Data）

企业数据通常分散在不同系统中，格式不统一，内容可能过期、重复或缺少元数据。很多重要信息也不是纯文本，而是图片、扫描 PDF、表格或演示文稿。

### 3.1 数据问题

- 文档碎片化、重复、缺页或缺少标题、作者、时间和版本等元数据；
- 内容来自图片、PDF、幻灯片、表格或扫描件，无法直接按纯文本处理；
- 同一事实在不同文档中存在冲突，旧版本可能与新版本同时被检索；
- OCR、表格解析和版面还原可能引入错误，影响后续 Embedding 和生成。

### 3.2 数据处理链路

```text
数据源盘点
  → 文档解析与 OCR
  → 清洗、去重、版本识别
  → 分块并补充元数据
  → Embedding 与索引
  → 抽样检查和持续更新
```

建议至少保留来源、文档版本、生效时间、更新时间、权限范围和解析状态等字段。对图片、PDF 和幻灯片，应根据内容类型选择 OCR、版面解析或表格提取工具，并对关键字段进行人工抽检。

### 3.3 检索侧控制

- 用文档类型、部门、时间、生效状态和权限做元数据过滤；
- 对版本冲突优先选择当前生效版本，并在回答中保留来源和时间；
- 对低置信度解析结果降低权重或进入人工复核队列；
- 通过去重、父子分块和相邻片段合并减少重复上下文。

## 4. 安全与隐私（Security and Privacy）

许多 RAG 系统用于处理企业专有资料、客户信息或其他敏感数据。安全性必须在数据接入、索引、检索、提示拼接、模型调用和日志记录的每一层落实。

### 4.1 核心风险

| 风险 | 示例 | 控制方式 |
| --- | --- | --- |
| 越权检索 | 用户检索到不属于其部门的文档 | 检索前执行身份、角色和文档级权限过滤 |
| 敏感信息泄露 | 回答或日志包含个人信息、密钥或内部数据 | 脱敏、最小权限、输出过滤和日志分级 |
| 提示注入 | 文档内容要求模型忽略系统指令 | 将检索内容视为不可信数据，隔离指令和上下文 |
| 数据外传 | 敏感上下文发送到不合规的模型服务 | 明确数据边界、加密传输并选择合规部署方式 |
| 过期内容 | 回答使用已失效的制度或配置 | 记录生效时间、版本并过滤失效文档 |

### 4.2 “默认私有”的设计原则

生产系统应默认只提供用户有权访问且当前有效的内容。权限过滤应尽量靠近检索入口执行，不能只依赖生成模型“自行遵守”；回答还应返回可审计的来源、版本和访问记录。

### 4.3 最小安全检查清单

- 知识库条目是否绑定了权限和数据分级？
- 检索结果是否在拼接提示词前再次校验权限？
- 是否对个人信息、密钥和凭证进行脱敏？
- 是否限制模型、工具和插件可访问的资源范围？
- 日志是否避免记录完整敏感提示词和上下文？
- 是否有数据删除、版本回滚和访问审计机制？

## 5. 生产落地检查框架

| 领域 | 最低要求 | 观测指标或证据 |
| --- | --- | --- |
| 性能 | 能承受目标并发，并有超时和降级路径 | QPS、P50/P95/P99、错误率、成本 |
| 请求处理 | 覆盖长尾、越界和恶意请求 | 拒答率、注入拦截率、按场景拆分的质量指标 |
| 数据质量 | 来源、版本和元数据可追踪 | 解析成功率、重复率、过期文档占比、抽检结果 |
| 安全隐私 | 权限先于生成，敏感数据受控 | 越权测试、审计日志、脱敏检查、访问记录 |
| 回答质量 | 有证据才回答，答案可追溯 | Recall@K、MRR、引用准确率、人工满意度 |

RAG 的生产能力不是单一模型指标，而是“数据管道 + 检索链路 + 模型调用 + 权限控制 + 监控评估”的整体结果。任何一环不稳定，都会表现为延迟升高、答案错误、拒答失效或敏感信息泄露。
