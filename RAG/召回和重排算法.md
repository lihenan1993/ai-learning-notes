# 召回和重排：BM25 与 RRF 融合

来源：字幕稿《BM25 为什么还能在 RAG 中发挥作用？》（2026-08-26 学习）+ 我自己的公式核对与实跑。
与另外两份笔记的边界：[RAG_检索器.md](RAG_检索器.md) 有 BM25 的基础定义与公式形状，[RAG_召回与重排.md](RAG_召回与重排.md) 有 Bi/Cross-Encoder 两阶段。本文只写这两份没有的：**三件套的实际数值行为、BM25 vs embedding 的失败边界、RRF 为什么必须用排名、链路分层与过滤位置、面试答法**。BM25 是什么这类定义不重复。

## 0. 一句话结论

BM25 管"字面对不对"，向量管"意思像不像"，RRF 管"两路排名怎么合成一个"——三者是**召回层的分工**，rerank 是下一层。
RRF 能不调权重，是因为它只用**名次**、不用分数，绕开了"BM25 分数无上界、cosine 有界"这个量纲不可比的死结。

## 1. BM25 的定位

- **定义**：Okapi BM25 是概率检索框架下的相关性评分函数。"Okapi"是伦敦城市大学（City University London）IR 系统的名字，BM25 在那里提出；概率检索框架由 Stephen Robertson、Karen Spärck Jones 等人在 1970-80 年代建立，TREC 系列论文（如 *Okapi at TREC-3*, 1994）给出工程化版本。字幕里"OCI 项目""ROBERSON"是 ASR 错字，说成"Okapi 项目 / Robertson"。
- **工业地位**：Lucene 的 `BM25Similarity` 默认 `k1=1.2, b=0.75`（2026-08-26 抓 javadoc 确认："Implemented as log(1 + (docCount - docFreq + 0.5)/(docFreq + 0.5))"，默认值同）；Elasticsearch / OpenSearch 的默认评分器就是它。所以"你用 ES 搜文档，谁排前面基本是 BM25 说了算"这句是对的。
- **一句话本质**：它不是在数词频，而是在"已知查询词分布"的先验下**估计每篇文档的相关性**，是个概率排序函数。

## 2. 三件套：公式 + 我真跑出来的数

```text
IDF(t)  = ln(1 + (N - df(t) + 0.5) / (df(t) + 0.5))          # N=文档总数, df=含该词的文档数
TF项     = f·(k1+1) / ( f + k1·(1 - b + b·dl/avgdl) )         # f=该词在本文档出现次数
score(q,d) = Σ_{t∈q} IDF(t) · TF项(t,d)
```

| 部件 | 解决什么 | 本质 |
| --- | --- | --- |
| IDF | 稀有词更值钱 | 全局统计出来的"稀有度权重"，`log(1+x)` 保证恒为正 |
| TF 饱和 | 刷词无效 | 词频收益递减，上限是 `k1+1` |
| 长度归一化 | 长文档不许靠篇幅取胜 | 用 `dl/avgdl` 折算命中"含金量" |

### 2.1 TF 饱和的真数（k1=1.2, b=0.75, dl=avgdl）

| 出现次数 f | 1 | 3 | 10 | 50 | 100 | 103 |
| --- | --- | --- | --- | --- | --- | --- |
| TF 项 | 1.0000 | 1.5714 | 1.9643 | 2.1484 | 2.1739 | 2.1747 |

上限 `k1+1 = 2.2`。**10 次 → 100 次（10 倍词频）只涨 11%；100 次 → 103 次基本为零。**这就是"刷词不划算"的数值形态。

> 字幕这里给的是 "f=10 时 tf_norm≈1.179，f=100 时≈1.196"。这两个数**和标准公式对不上**（同一个分母不可能同时成立），按 Lucene 公式应为 1.964 / 2.174。结论（边际递减）没错，数字别背错。

### 2.2 IDF 的真数（N=10000）

| df | 1 | 10 | 1000 | 8000 |
| --- | --- | --- | --- | --- |
| IDF | 8.81 | 6.86 | 2.30 | 0.22 |

现象：越稀有越接近 9 分，越常见越接近 0，但**永远为正**（`log(1+x)` 的功劳，`+0.5` 平滑防 df=0 除零）。所以"403"这种错误码在运维文档里 df 极小，权重会被顶到最高——这正是 BM25 在运维排障场景的价值。

### 2.3 长度归一化

`dl/avgdl` 越大，分母越大，惩罚越狠。`b=0` 完全不看长度，`b=1` 完全按比例惩罚。实跑对照：一篇命中 `deploy`+`403` 但长了 5 倍多的文档被压到 0.762，短文档 1.336（见 `bm25_rrf_demo.py` 输出）。

## 3. BM25 相对 TF-IDF 修的两个坑

| | TF-IDF | BM25 |
| --- | --- | --- |
| 词频 | 线性加权，刷 1000 次分数就堆上去 | 饱和封顶，翻倍刷不会翻倍 |
| 长度 | 无归一化，长文天然高分 | `b` 参数按 `dl/avgdl` 校准 |
| 结果 | "提到 1000 次"的长文能压过"出现 3 次"的正文 | 短而精的排前面 |

一句话答面试官：**BM25 变成工业默认不是因为复杂，是因为把 TF-IDF 两个会被业务玩坏的坑补了。**

## 4. 纯向量为什么会在真实业务里翻车（混合检索的动机）

| 场景 | 例子 | 向量怎么错 | BM25 怎么救 |
| --- | --- | --- | --- |
| 精确标识符 | `payment_gateway timeout`、`403` | 把 timeout 和 rejected 拉得很近，真日志被挤到后面 | IDF 给低频术语打高分，精准顶回第一 |
| 版本号 / 配置项 | `v3.2`、`PAYMENT_V2_ENFORCE` | 这类字符串在 embedding 里几乎没有语义 | 不管含义，字面越稀罕权重越高 |
| 运维知识库 | "部署失败 403 要解决方案" | 推一堆泛"权限问题"文档，缺那条 403 原文 | 词面命中就是命中 |

字幕转述的 InfoQ runbook 反例（**我没核到原文，按讲者转述记**）：某公司纯向量检索"如何启用某功能"，把"禁用该功能手册"排到第一，因为语义太像；后来加 BM25 + RRF 混合检索立刻纠正——`启用`/`禁用` 是两个不同 token，词面一拉就分开。
这和我 10-16 实测的"配置改了怎么不重启生效"是同一类失败：向量被表面重叠骗了，只是那次靠 rerank 救回来，这类**精确 token 型**问题靠 BM25 更便宜。

## 5. RRF（Reciprocal Rank Fusion）

### 5.1 为什么不能加权求和

| 侧 | 分数形态 |
| --- | --- |
| BM25 | 无上界，几分到几十都可能，受 k1/b/语料统计影响 |
| 向量 | cosine 落在 [-1, 1]（Milvus 的 COSINE 指标返回的是距离，用前注意换算） |

量纲完全不同，直接相加等于"谁的量纲大谁话事"。就算先归一化（min-max / z-score / sigmoid），归一化方式本身要调，且分数分布随 query 漂移——面试官问"权重怎么定"就是卡在这。

### 5.2 公式

```text
RRF(d) = Σ_i  1 / (k + rank_i(d))      # 缺席的那一路记 0；k 默认 60
```

`k=60` 来自 Cormack / Clarke / Büttcher, *Reciprocal Rank Fusion outperforms Condorcet and individual Rank Learning Methods*, SIGIR 2009；ES、OpenSearch、Weaviate、Qdrant、Milvus 的默认实现都取 60。原文自己也说 k 不敏感（20~100 之间 MAP 几乎不动）。

### 5.3 实跑出来的数（k=60）

| 名次 | 1 | 3 | 10 | 20 |
| --- | --- | --- | --- | --- |
| 1/(k+rank) | 0.0164 | 0.0159 | 0.0143 | 0.0125 |

k 的作用是**陡峭度**：k=10 时第 1 名 0.0909、第 5 名 0.0667（差 26%）；k=60 时第 1 名 0.0164、第 5 名 0.0154（差 6%）；k=100 更平，适合"拉到 100 条喂 rerank"。

**最关键的工程性质**：两路都把同一篇排在前面 → 它几乎必胜。

```text
T: BM25 第2 + 向量第3 → 1/62 + 1/63 = 0.0320
S: BM25 第1，向量缺席 → 1/61        = 0.0164   ← 单路第一也输
```

这就是"不用为每个 query 调权重"的原因：共识比单点强势更值钱。

### 5.4 边界

1. **RRF 丢掉分数信息**。某一路以 0.99 高置信命中、另一路只是勉强进前 50 时，RRF 看不出差别。两路质量差距大时，`WeightedRanker`（先归一化再加权）或直接 rerank 更合适。
2. **RRF 不解决单路漏召回**。一路没捞到，融合里就是 0 分，救不回来。
3. **两路候选池要覆写同一批 chunk id**，否则融合等于拼接。别一边用 `chunk_id` 一边用 `doc_id`。

## 6. 工业链路的分层与两条纪律

```text
[metadata/权限过滤] → BM25 倒排召回(topN) ┐
                    → 向量 ANN 召回(topN) ┴→ RRF 融合 → rerank → Top 3-5 进上下文
```

- **纪律一：过滤必须前置（至少在融合之前）**。敏感文档一旦混进候选池，rerank 或 LLM 都可能已被污染，而且白付算力。安全要从源头设计，不是最后再筛一遍。
- **纪律二：规模阈值只当经验，不当定理**。字幕给的是"<10 万纯向量够 / 10 万-1000 万必须混合 / >1000 万必须加 reranker"，**这是讲者的经验值，我没有核实依据**。真实决策要看你自己的 eval 集（recall@k、NDCG@10）。这条如果照背会翻车，面试时要说"经验区间，具体看评估集"。

## 7. 参数与中文场景

| 参数 | 默认 | 作用 | 讲者经验（未验证） |
| --- | --- | --- | --- |
| k1 | 1.2 | 控饱和速度，调大 → 需要更多次命中才饱和 | 1.2 最稳 |
| b | 0.75 | 控长度惩罚强度 | 文档 >2000 字 b→0.9；短字段 b→0.3 |

我补的边界：这两个是英文 TREC 语料调出来的默认值，**中文场景下分词器的影响远大于调 b**。ES 的 IK/smartcn、Milvus 2.5+ 的 sparse + analyzer 决定 term 粒度，直接改写 `df` 和 `dl`；分词不对，公式再对也没用。工程上先定分词，再谈调参。

## 8. Go / 广告类比

| 概念 | 对应物 |
| --- | --- |
| BM25 倒排 + IDF | Offer 检索粗排：term 命中 + 全量统计出来的权重表 |
| 向量召回 | 语义近邻召回：跨域泛化好，但精确 id 不可靠 |
| RRF | 多路召回各出一份 topN，按名次合并（不用对齐两侧 score） |
| rerank | 精排模型，逐条算重特征 |
| 过滤前置 | 广告投放的定向/黑名单必须在召回前做，召回后再筛既浪费算力又可能出不该出的广告 |

## 9. 面试答法（30 秒版，结论 → 原理 → 边界 → 项目）

**BM25（4 句话模板）**

1. 定义：BM25 是概率检索框架下的相关性评分函数，由 Robertson 等人在 Okapi 系统上提出，是 ES/OpenSearch 的默认评分器。
2. 三件套：IDF 让稀有词值钱、TF 饱和让刷词失效（上限 k1+1）、长度归一化让长文档吃亏。
3. 例子：搜"部署失败 403"，403 的 df 极小、IDF 极高，一搜就精准命中；纯向量会推一堆泛权限文档。
4. 参数：k1=1.2、b=0.75 是 Lucene 默认，评测集大量验证过，不最优但几乎不翻车；中文先定分词再调参。

**RRF（被问"怎么融合"时）**

结论：用排名融合不用分数加权，因为 BM25 分数无上界、cosine 有界，量纲不可比。
原理：`1/(k+rank)` 求和，k=60 来自 Cormack 2009，第 1 名 0.0164、第 10 名 0.0143，陡峭度低但足以让"两路共识"胜出（实测 T 双路 2/3 → 0.0320 反超单路第一 0.0164）。
边界：丢分数信息，两路置信度差异大时会吃亏；不救漏召回；过滤必须在融合前。
示例：运维排障知识库里，`403` / `DEPLOY_FAILED` 这类查询向量会翻车，所以召回走 BM25+向量双路 → RRF(k=60) → qwen3-rerank 取 Top 3-5。**（示例设计，非线上方案。）**

## 11. Milvus 里的 BM25：API 与实测坑

```python
schema.add_field("text", DataType.VARCHAR, max_length=1024,
                 enable_analyzer=True, analyzer_params={"tokenizer": "jieba"})
schema.add_field("sparse", DataType.SPARSE_FLOAT_VECTOR)
schema.add_function(Function(name="text_bm25", function_type=FunctionType.BM25,
                             input_field_names=["text"], output_field_names=["sparse"]))

index_params.add_index(field_name="sparse", index_type="SPARSE_INVERTED_INDEX",
                       metric_type="BM25",
                       params={"inverted_index_algo": "DAAT_MAXSCORE",
                               "bm25_k1": 1.2, "bm25_b": 0.75})

client.search(coll, data=["部署失败 403"], anns_field="sparse",
              search_params={"metric_type": "BM25"}, limit=3)
```

实测结论（每条都是跑出来的，不是猜的）：

| 项 | 结果 |
| --- | --- |
| BM25 全文检索 | 跑通。query 直接传原文，服务端用同一个 analyzer 编码 query |
| 返回分数 | **负数距离**，如 `-2.6995`；分数越高越负，排序按 distance 升序，别按降序 |
| sparse 向量 | 服务端自动生成，term id 是哈希后的整数、值多为 1.0；**不能自己构造 query sparse，必须传文本** |
| hybrid_search + `RRFRanker(60)` | 跑通，分数正好 `1/(60+rank)`（第 1 名 0.0164），验证 k=60 默认 |
| `WeightedRanker(0.7, 0.3)` | 跑通，输出已归一化（带 `norm_score=True`） |
| 中文 | 必须 `analyzer_params={"tokenizer": "jieba"}` + `pip install jieba`；内建 `chinese` analyzer 在 Lite 报 `unknown tokenizer type`（Lite 只支持 `standard`/`jieba`） |
| `DataType.TEXT` | Lite 不支持（报 `MilvusLite does not support`），用 `VARCHAR + max_length` |
| `bm25_k1` / `bm25_b` | 官方文档说放 index `params` 里，但 **Milvus Lite 实测不生效**：k1=0 / 1.2 / 5.0 三组分数完全一致，`describe_index` 也不回显。调参必须连真 Milvus server |
